# Settings UI — one catalogue, two screens

Status: **v1 built, 2026-10-30.** This note is the design of the settings surface: the pre-game launcher, the Mac settings
window and the in-game menu. It supersedes the menu's hard-coded row list (recorded as v1 in
[`ingamemenu-v2.md`](ingamemenu-v2.md) §7) and keeps that note's overlay, live/next-start honesty and store rules. Every claim
about the code below carries a `file:line`; the line numbers are of this change.

The one-line goal: **the in-game menu is the launcher's list, for the running game.** Not a subset, not a second list, no row
twice — every setting the app ships, under the same heading, with a badge that says whether a change is in effect now or at
the next start.

---

## 1. The catalogue: where a setting comes from

Three files, one direction:

1. **`docs/env_switches.tsv`** — every `DM_*` switch the code reads: 320 rows, each with a class (`player`, `path`, `switch`,
   `diagnostic`, `test`), generated by `dm/tools/env_switches.py` from the sources and kept by hand. 22 rows are `player`
   (a launcher setting) *before* this change; the two rows added here (`DM_AUDIO`, `DM_PAD_MERGE`) are still classed
   `switch` in that table — see §9, follow-up 1, because `docs/` is outside this change's file set.
2. **`dm/games/settings.tsv`** — the player-facing subset: **24 rows** (`:19-48`), eight columns (`variable`, `kind`, `default`,
   `shown`, `section`, `label`, `note`, and the optional `meta`; header `:1-18` documents them).
3. **`dm/games/settings.py`** — filters that catalogue for one game and writes `dm/launcher.json`, which every screen decodes:
   - `SECTIONS = ('Game','Screen','Controls','Performance')` (`:13`) validates the `section` column;
   - `META = {level, needs}` (`:17-20`) is the only optional per-row metadata (this sprint adds no key, because a new key must
     also land in `docs/frontends.md` and `docs/launcher.schema.json`, which are outside this change);
   - `shown(cond)` (`:71-80`) resolves `always`, `languages>1`, `fixups:<KEY>`, `gfxapi:<API>`, `platform:<ios|mac>` and
     `DM_GAME_<NAME>== / != <value>` — so a row exists in an app only if that game can honour it;
   - `needs` validation (`:100-104`) refuses a sub-setting that names a variable no row sets;
   - the written row carries `section`, `label`, `note`, `default`, the kind's own fields and `needs`/`level` (`:106-122`).

Breadth of that catalogue for Breath of the Wild (`01007EF00011E000`, `GFXAPI=nvn`, two languages): **23 rows on iOS, 19 on
Mac** (the Mac list drops the touch-pad rows and the frame-rate counter, and adds Display mode). The remaining ~300 switches
are diagnostics, paths, build-time knobs or tests — §7 explains which ones were considered and why they stay out.

## 2. The taxonomy: what ARMSX2 does, and what this product can honestly do

### 2.1 The reference

ARMSX2 is a PCSX2 fork; its Qt settings dialog is the reference for grouping, naming and live-vs-restart presentation. Read
from the shipped app (`~/Applications/ARMSX2.app`, `net.armsx2.armsx2`, version `90126bdfea`) and its data
(`~/Library/Application Support/ARMSX2`, `inis/PCSX2.ini`):

- **One category per page**, in a fixed order: *Interface, Game List, Emulation, BIOS, Graphics, On-Screen Display, Audio,
  Memory Cards, Network & HDD, Folders, Achievements* (the category list in `Contents/MacOS/ARMSX2`). Categories are the
  player's mental model ("Graphics", "Audio"), not the code's modules.
- **Two levels**: the pages show what a player needs; a single global **"Show Advanced Settings"** switch (menu item, same
  binary) reveals the tuning rows. PCSX2 calls the second set the renderer's expert rows.
- **Every setting carries a description**, and options are enumerated in it — e.g. *Dithering*: "Reduces banding between
  colors… Off: Disables any dithering. Scaled: Upscaling-aware / Highest dithering effect. Unscaled: Native dithering…".
- **Restart-required settings say so in the row itself**, not in a modal: *Use Threaded Presentation* ends with "Takes effect
  when the game restarts."; the GPU-driver page says "A driver takes effect the next time ARMSX2 starts" and offers
  **Apply & Restart**.
- **A per-game layer**: *Game Properties* and per-game settings sit beside the global ones, and `gamesettings/` in its data
  folder holds them. (PCSX2's pattern: global defaults, per-game overrides.)
- Its ini is grouped to match: `[EmuCore]`, `[EmuCore/Speedhacks]`, `[EmuCore/CPU]`, `[Graphics]`, `[Audio]`, `[Folders]` …
  (`inis/PCSX2.ini`).

NX2Apple (the Mac front end for this product, MIT) is the second reference for the *look*: `settingsPage` is a list of
**cards**, each a heading with a footnote, and rows of `title – detail – trailing control`
(`frontend/Sources/NSPortBuilder/ContentView.swift:3426` `settingsPage`, rows `:3445-3461`, as of `main` 2026-10-30). A Mac
settings surface reads as labelled rows with a line of explanation, not as a wall of unlabelled switches.

### 2.2 The four sections this product can have

The mapping is the reference's pages minus what this product does not have:

| Our section | ARMSX2 pages it stands for | What it holds here |
|---|---|---|
| **Game** | Emulation (+ the game's own identity) | frame rate, render scale, dynamic resolution, console mode, upscaling, language, frame-rate counter, display mode, sound |
| **Screen** | Graphics' display half, On-Screen Display | picture fill, split when upright |
| **Controls** | Controllers | touch feedback, rumble (+ strength, cutoff), pad layout, on-screen controls, merge controllers |
| **Performance** | Graphics' renderer half, Speedhacks | frame buffering, Metal 4 pipelines, pipeline prebuild, encode thread, hold frames, performance HUD |

This is the fixed section set, and the reason is a contract, not taste: `dm/tools/tests/test_launcher_settings.py` pins the
four section names, their order and the exact Performance row list for Breath of the Wild
(`test_sections_keep_the_profile_defaults`: `['Game','Screen','Controls','Performance']` and `PERFORMANCE_NVN`), and
`dm/ios/tests/launcher_storage_check.swift:72-73` pins the Mac window's Basic/Advanced sections and Basic row order. Both
files are outside this change's writable set, so a fifth section ("Audio") would fail the sprint's own verification command.

Consequences, stated plainly instead of hidden:

- **Audio has one switch** (`DM_AUDIO`), so it lives at the end of **Game** (`settings.tsv:30`) with the label *Sound*. When
  a fifth section is permitted (§9, follow-up 2), the row moves unchanged — `section` is data, and schema 1 already says a
  reader draws an unknown section like the others (`docs/frontends.md`, *Compatibility*).
- **Sound is an Advanced row on the Mac.** The Mac window's Basic rows are pinned to the five Game rows the storage
  check names (`launcher_storage_check.swift:73`), so `DM_AUDIO` shows under *Advanced settings* there; the Mac window is
  a secondary surface for this product and the row is one disclosure away.
- **No Basic/Advanced on iOS.** The Mac window keeps its Basic-first / "Advanced settings" disclosure (`level=basic`, five
  Basic rows in Game plus Game rumble), exactly as PCSX2's global "Show Advanced Settings". The iOS launcher and the menu
  show one list with a search field, because a phone has no second column.
- **The labels are sentences, not switch names** — "Hold frames when late", not `DM_FPS_HOLD` — and each row carries the
  catalogue's `note` as its description, in the reference's style (what it costs: latency, memory, heat).

## 3. One model, two screens

    dm/games/settings.tsv ──settings.py──▶ dm/launcher.json ──▶ SettingsFile (decode)
                                                                     │
                                         ┌───────────────────────────┴───────────────────────────┐
                                   LauncherModel / LauncherView                     InGameMenuModel / InGameMenuView
                                   (iOS launcher, Mac window)                         (in-game overlay)
                                         └────────── SettingsGrouping.sections(…) ──────────────┘
                                                                     │
                                                             SettingsStore  (`launcher.<VAR>`)

| Piece | Where |
|---|---|
| One grouping for every screen: section order from the catalogue, the `needs` rule, an optional search filter, an optional Basic/Advanced split | `dm/ios/Sources/LauncherSettings.swift:37-76` (`SettingSection`, `SettingsGrouping`) |
| The launcher and the Mac window draw those groups | `dm/ios/Sources/Launcher.swift:116-121` (`m.groups`); `dm/mac/Launcher.swift:63-72`, whose Form asks for `sections(basic:)` / `rows(in:basic:)` — two shapes over the same grouping (`LauncherSettings.swift:151-159`) |
| The menu draws the same groups from the same file, with no list of its own | `dm/ios/Sources/InGameMenu.swift:62` (`sections`), `:97` (`reset(section:)`), `:102` (`resetAll`) |
| One store, one key: a choice is `launcher.<VAR>`, a default stores nothing, an env file's value is fixed | `LauncherSettings.swift:81-132` |
| Live or next start, per row, asked before the player touches it | `dm/ios/Sources/settings_live.m:92` (`dm_setting_live_state`) |
| Commit: persist through the store, then run the live path — never `setenv` | `InGameMenu.swift:74-93` |

The in-game menu's shape (unchanged from `ingamemenu-v2.md` §2, now catalogue-driven):

- a scrim over the running game (tap closes) and a 360 pt dark panel on the trailing edge;
- a header with **Done**; a **Search settings** field appears when the catalogue has more than 8 rows
  (`InGameMenu.swift:229-241`) — it matches a row's name, description, switch or heading, and drops a section with no match;
- one block per catalogue section, rows in catalogue order; a row is `name  ·  badge` / control / description
  (`InGameMenu.swift:119-159`), the badge being **Applies now** (green), **Next start**, **Set by an env file** or
  **Set at launch**;
- a **Reset** beside a section heading, offered only when a row in it differs from its default and resetting only that
  section (`InGameMenu.swift:97-100`, `:250-266`); **Reset to tested defaults** in the footer keeps its existing rule;
- Control positions (Move / Play, Reset positions) stays at the end of Controls as the pad's session state, not a stored
  setting, and is hidden while a search is active;
- a footer **status strip**: "Now 59 fps · thermal: nominal", the 30 fps thermal-hold note, Reset, Done
  (`InGameMenu.swift:285-308`).

Both screens read one `dm/launcher.json`, so *iOS launcher ≡ iOS menu*, row for row, including `needs` visibility (a row
hidden because its parent is off is hidden on both). The Mac window reads the Mac build of the same catalogue.

## 5. Live changes: what the bridge can do, and what it refuses to fake

`dm_setting_live(env, value)` returns 1 only when the change is in effect now; `value == NULL` asks without side effects, so
the badge is drawn before the player touches anything (`settings_live.m:40-92`). No `setenv` on this path: the environment
stays the launch-time record, because the host calls `getenv` from the present, audio and guest threads.

| Row | Live path | Added here |
|---|---|---|
| Frame rate | `dm_fps_state_set_fps` (`loader.c:236`) | no |
| Render scale | `dm_fps_state_set_scale` (`loader.c:240`) | no |
| Picture fill | `dm_present_set_fill` (`nvn_mtl.m:11122`) | no |
| Split when upright | `dm_dual_set` (`DmGamepad.m:276`) | no |
| Game rumble | `dm_haptics_apple_set` (`haptics_apple.m:436`) | no |
| Pad layout / On-screen controls | `dm_gamepad_set_layout` / `_set_hidden` | no |
| **Touch feedback** | `dm_gamepad_set_touch_haptics` → `applyTouchHaptics` (`DmGamepad.m:611-615`, `:737-741`) | **yes** |
| **Performance HUD** | `dm_hud_set` → the layer's `developerHUDProperties` (`front_ios.m:209-217`) | **yes** |

Why the rest stay next-start (each is a real limit, not laziness):

- **Rumble strength / cutoff** want `dm_haptics_apple_set(on, gain, min)`, which requires the *on* value as well — a
  parameter the menu's row does not carry. A correct live path needs a small `dm_haptics_apple_set_gain/min` in
  `dm/host/haptics_apple.m`, and `dm/host` is outside this change (§9, follow-up 3).
- **Upscaling** would be one line in `dm/gfx/nvn/nvn_mtl.m` (the mode *is* read per present, `:11207`); `dm/gfx` is out of
  scope and the pipeline is not to be touched for a convenience.
- **Console mode, game language, dynamic resolution** write state a game reads once and builds UI/render targets around;
  a live change can break a game (`ingamemenu-v2.md` §1 pins this reasoning).
- **Frame buffering, Metal 4 pipelines, pipeline prebuild, encode thread** allocate GPU objects and choose code paths at
  start; **frame-rate counter** would need the label created and torn down in `front_ios.m`; **Sound** is read per
  `OpenAudioOut` and a game opens its output at boot; **merge controllers** reassigns players mid-session, which would strand
  held inputs.

## 6. v1 scope

Shipped:

1. The menu is **catalogue-driven**: rows, sections and order come from `dm/launcher.json` through `SettingsGrouping`; the
   hard-coded list is gone (`InGameMenu.swift:17-117`).
2. **One grouping** shared by the iOS launcher, the Mac window and the menu (`LauncherSettings.swift:37-76`), with the
   `needs` rule in one place.
3. **Per-row badge** (Applies now / Next start / Set by an env file / Set at launch) and **description** (the catalogue's note,
   or what the last change did).

## 7. Deliberately left out

| Switch(es) | Why not a row |
|---|---|
| `DM_PRESENT_LATENCY`, `DM_PRESENT_FIFO`, `DM_PRESENT_HZ`, `DM_PRESENT_LINK`, `DM_PRESENT_INTERVAL` | Present pacing. Uncapped/latency change what the game's logic sees and cost power/heat; and they would be Performance rows, whose list this sprint cannot extend (§2.2). Environment-only, as today. |
| `DM_THERMAL_CAP` | Offering "off" is a promise to overheat the phone. The host's 30 fps hold is a safety rule, not a preference (`hle_nvn.c:1610-1621`). |
| `DM_ASPECT`, `DM_DUO_ASPECT` | Change the picture's geometry or the camera ratio; wrong values distort the world. Build-time/env only (`ingamemenu-v2.md` §1). |
| `DM_MOTION`, `DM_PHONE_MOTION`, `DM_SHAKE_G`, `DM_MOTION_GAIN` | No `shown` condition can tell whether the build carries motion code (the NSP script's `--no-motion` bakes `DM_MOTION=0` in), so a row could offer a switch that does nothing; the phone-only ones would also change the iOS/Mac row sets the tests pin. |
| `DM_SCREEN_MATCH`, `DM_KBD_PLAYER` | Mac-only rows; adding one would change the pinned platform difference (`test_iphone_switches_only_on_the_iphone`). |
| `DM_UE_TEXTURE_POOL` | Per-engine (Unreal) and the "game's own" value is `0`, which the `range` kind cannot express; no condition in the catalogue identifies an Unreal pack. |
| `DM_FPS` | A second spelling of Frame rate (`DM_FPS_TARGET`); keeping both would be the duplicate this sprint removes. |
| `DM_LAUNCHER`, `DM_SAVED_CHOICES` | Switches *of* the settings screens; a player inside the menu has already answered them. |
| `DM_SAVE_SYNC` | Already a section of its own (Cloud saves) in both launchers; a folder is not one of the three kinds. |
| `DM_AUDIO_MUTE`, `DM_DBG_AU_FRAMES`, and the ~300 others | Diagnostic/path/build/test switches, by definition not player-facing (`docs/development.md`, the classes). |

## 8. Limits and known costs

- **Nothing was seen on a phone.** The overlay, the search field and the two new live rows are typechecked against the iPhone
  SDK and the models are exercised on macOS; no frame was rendered.
- **The menu's live table is per build.** A row's badge is honest per *build*, not per *state*: e.g. Frame rate says
  "Applies now" only when the loader wrote a frame-step page (aspects of some builds have none).
- **Search is a filter, not an index.** It matches case-insensitively on name, description, switch and heading; `DM_` names
  are matched so a player who knows the switch can find it.
- **`docs/settings.md` and `docs/env_switches.tsv` are now one edit behind** (the new rows and the two class columns). They
  are outside this change's file set; §9 carries them.
