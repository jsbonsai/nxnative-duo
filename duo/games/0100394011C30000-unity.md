# Scott Pilgrim vs The World: The Game — the Duo aspect lever

Build `8b939dc403aa7e4817de4f646ff72d86` (v196608, `main` at
`/path/to/work/0100394011C30000_build/extract/v196608/ExeFS/main`).
All offsets below are **image offsets** (text at 0, `TEXT_END 0xfa6ee0`, ro at
`0xfa7000`, data at `0x17c4000`), i.e. what `patch_nso.py` rewrites — the same
numbering `duo/research/res.tsv` and `duo/research/games.tsv` use.

## 0. The premise is wrong: this game is not Unity

The ticket says "Unity's player". It is not: `main` contains no `Unity`/`il2cpp`/
`Assembly-CSharp` strings, and it imports `_ZN2nv18InitializeGraphicsEPvm`,
`_ZN2nv20SetGraphicsAllocatorE…` and `nn::vi::CreateLayer/GetNativeWindow`, which is
Ubisoft's NVN engine on NintendoSDK_NVN 10.6 (see `dm/games/0100394011C30000/game.tsv`
and the survey). That matters: there is no `Screen.SetResolution`-style path to look
for, and no managed display config. Everything below is engine code in `main`.

## 1. What the log line actually reports

`dm/gfx/nvn/hle_nvn.c:1290`

```c
LOG("[nvn] WindowInitialize swap chain %d textures, interval %d, first %dx%d format %#x", …,
    (int)CTX(o->tex[0])->d.width, (int)CTX(o->tex[0])->d.height, …);
```

So `first 1920x1080` is **the first swap-chain texture's own dimensions**, which the
guest set with `nvnTextureBuilderSetSize2D` (`hle_nvn.c:2155`:
`TB(b)->d.width = w; TB(b)->d.height = h;`). It is not a host decision — the host never
chooses a size. That is why the old `duo/research/res.tsv` render-size row (§4) could not change it.

## 2. Finding the guest's SetSize2D call sites

The guest resolves NVN through the proc table: a resolver loop at `0x632238`…
`0x634xxx` calls the `nvnDeviceGetProcAddress` function (obtained by
`nvnBootstrapLoader("nvnDeviceGetProcAddress")` at `0xea934c`) once per name string and
stores each result through a GOT slot. For `nvnTextureBuilderSetSize2D`
(string at `0x132e461`, name ref at `0x633230`):

| step | address |
|---|---|
| `adrp x8, #0x18ff000; ldr x8, [x8, #0xfc8]; str x0, [x8]` (store the resolved fn) | `0x633240` |
| GOT slot `0x18fffc8` → `R_AARCH64_RELATIVE` addend = the global holding the pointer | `0x191da90` |
| the only two code sites that load `0x191da90` | `0xeaa734`, `0xeabdc4` |

Both sites are the same six-call texture-builder sequence (SetDefaults, SetDevice,
SetTarget 9, **SetSize2D**, SetSamples 1, SetFormat 0x25 …):

```
0xeaa734  adrp x8, #0x191d000           0xeabdc4  adrp x8, #0x191d000
0xeaa738  ldr  x8, [x8, #0xa90]         0xeabdc8  ldr  x8, [x8, #0xa90]
0xeaa73c  mov  w2, #0x438   ; 1080      0xeabdcc  mov  w2, #0x438   ; 1080
0xeaa740  add  x0, sp, #0x70            0xeabdd0  add  x0, sp, #0x48
0xeaa744  mov  w1, #0x780   ; 1920      0xeabdd4  mov  w1, #0x780   ; 1920
0xeaa748  blr  x8                       0xeabdd8  blr  x8
```

`nvnTextureBuilderSetSize2D(builder, w1, h2)` → **1920x1080, hard-coded in code**, in two
functions:

* `0xea9280` (`0xeaa734` = +0x14b4) — the renderer init, which also does
  `nv::InitializeGraphics`, `vi::OpenDefaultDisplay/CreateLayer/GetNativeWindow`.
* `0xeabcf0` (`0xeabdc4` = +0xd4) — the swap-chain builder; it is called from
  `0xeaa8b4` and calls `nvnWindowBuilderSetTextures` at `0xeac114`.

These are the **only** `SetSize2D` call sites in `main` (all other textures are built
with `SetWidth`/`SetHeight` from a descriptor struct), so they are the only place the
1920x1080 canvas comes from.

Note the swap-chain builder is *passed* a size struct (`sp+0x5c`, built at `0xeaa1e8`
from the engine display size) but **ignores it for the texture**: it builds the builder
from the immediates above, and only copies the passed struct's w/h into its own object at
`0xeac14c`/`0xeac154` (`[x20+0x24]`, `[x20+0x28]`). Both numbers must agree, which is
why the patch touches both sources.

## 3. Where the engine's display size comes from

`0xea9300`..`0xea9330` (renderer init):

```
0xea9300  bl   nn::oe::GetPerformanceMode
0xea9304  mov  w21, #0x2d0          ; h = 720   (handheld default)
0xea9308  mov  w26, #0x500          ; w = 1280
0xea930c  cbz  w0, 0xea9334         ; perf mode 0 → keep 1280x720
0xea9318  bl   nn::oe::GetDefaultDisplayResolution(&w, &h)
0xea9320  cmp  w8, #0x438           ; h vs 1080
0xea9324  mov  w8, #0x780           ; 1920
0xea9328  csel w26, w26, w8, lt     ; h < 1080 → 1280, else 1920
0xea932c  mov  w8, #0x438           ; 1080
0xea9330  csel w21, w21, w8, lt     ; h < 1080 →  720, else 1080
```

The host answers `GetDefaultDisplayResolution` with the operation mode's panel
(`dm/host/hle_oe.c:151`: 1920x1080 console, 1280x720 handheld) and
`GetPerformanceMode` with the console/boost mode, so the game picks **1920x1080** —
this is the value it then hands to the swap-chain builder at `0xeaa8b4` and records as
the renderer's own size.

The same 1080/1920 pair is repeated in the notification handler at
`0xe96660` (`0xe96730`/`0xe9673c`), which only runs on an operation-mode change
notification (`TryPopNotificationMessage`); the host pushes one only when the iOS front
end changes the mode (`dm/host/hle_oe.c` `dm_set_opmode`). It writes the app-level
display size at `[obj+0x328]`/`[obj+0x32c]`, not the render size, and its
`min(actual, default)` clamp (`0xe9675c`) would put 1080 back anyway — so it is left
alone.

## 4. Why the existing `duo/research/res.tsv` row is wrong

The row patched the `1280x720` u32 pair at `0x13330c8`. That address has **no reader**:

* no `adrp`+`add` / `adrp`+`ldr` (w/x/s/q, ±0x10) anywhere in text reaches
  `0x13330c0..0x13330cc`;
* no `R_AARCH64_RELATIVE` relocation points into `0x1333000..0x1333200`, so it is not
  in a pointer table either;
* the bytes around it are unrelated floats (`160.0, 120.0, 1280, 720, …`), i.e. a
  coincidental pair in a constant blob.

The 1280x720 pairs the engine *does* read are elsewhere and are default video settings,
not the render size: `0x13355a0` `{1280,720,1,0}` (stored into settings objects at
`0x757f9c`, `0x75b7ac`, `0x9b13b0`, `0x9b378c`, `0xc40ac8`), `0x13358a0` `{1280,720,60,28}`
(getter at `0xeacff0`), `0x13361b0`. Patching any of them changes a saved/default
setting, not the canvas.

## 5. There is no 16:9 aspect in `main` to patch

* The only `1.7777778f` (`0x3FE38E39`) is at `0x13340c8`, inside a generic float blob,
  and has **no xref** in `main` (same scan as above). (`sdk` has one at `0xa4bd64`, in
  libnvn/nnSdk constants, also unrelated to this game's camera.)
* No `fdiv` in `main` divides two width/height-derived floats: all 483 `fdiv` sites were
  traced to their operands' definitions, and the only ones fed by two int→float
  conversions (`0x257650`, `0x2576e8`, `0x25771c`, `0x2586d8`, `0xb164bc`, …) are
  gameplay threshold comparisons (`[x19+0x114]/[x19+0x118]`), not a projection.
* No `fdiv` takes both operands from two adjacent struct fields.

So the projection cannot be hard-coded to 16:9 in this binary: whatever the camera uses
is a runtime size, and the only runtime sizes are the render size (1920x1080) and the
canvas (1920x1080). **Make both 1.4222 and both hypotheses are satisfied.**

## 6. The patch

Four words, each `movz` immediate (assert the original before writing):

| offset | original word | new word | bytes (old → new) | meaning |
|---|---|---|---|---|
| `0xea9304` | `0x52805a15` `mov w21, #0x2d0` | `0x52807095` `mov w21, #0x384` | `15 5a 80 52` → `95 70 80 52` | handheld render height 720 → 900 (1280x900 = 1.4222) |
| `0xea932c` | `0x52808708` `mov w8, #0x438` | `0x5280a8c8` `mov w8, #0x546` | `08 87 80 52` → `c8 a8 80 52` | console render height 1080 → 1350 (1920x1350 = 1.4222) |
| `0xeaa73c` | `0x52808702` `mov w2, #0x438` | `0x5280a8c2` `mov w2, #0x546` | `02 87 80 52` → `c2 a8 80 52` | swap-chain texture height 1080 → 1350 |
| `0xeabdcc` | `0x52808702` `mov w2, #0x438` | `0x5280a8c2` `mov w2, #0x546` | `02 87 80 52` → `c2 a8 80 52` | swap-chain texture height 1080 → 1350 |

Widths stay 1920 (`0x32190fe1` at `0xeaa744`/`0xeabdd4`, `0x32190fe8` at `0xea9324`):
keeping the width and growing the height shows **more world vertically and loses nothing
horizontally**, which is the safe direction for a side-scrolling brawler, and it keeps
the horizontal pixel scale 1:1 (1920 px stays 1920 px of world).

1920x1350 = 1.42222 against the Duo's 2853x2007 = 1.42152 — 0.05 % off, the same
tolerance `duo/DESIGN.md` accepts for 2048x1440. If exactness is wanted, use `#0x547`
(1351 → 1.42117, 0.03 % the other way): `0x5280a8c8`→`0x5280a8e8` and
`0x5280a8c2`→`0x5280a8e2`. Everything else is unchanged.

Do **not** touch `0xea9320` (`cmp w8, #0x438`): that is the threshold against the real
panel height (1080 on the host), and raising it would make the game fall back to
1280x720.

### Why all four and not just the swap chain

`0xea932c` sets the engine's display size, which becomes the render size and is handed
to the swap-chain builder; `0xeaa73c`/`0xeabdcc` are the hard-coded values that builder
actually uses for the textures. Patch only the swap chain and the renderer thinks its
canvas is 1350 tall while the textures are 1080 (the game's own blit then squeezes
1.4222 into 16:9); patch only the display size and the textures stay 1080. Both must
move together. `0xea9304` is the same for the handheld branch (the iOS front end can
downgrade the operation mode on overheat, `dm_set_opmode`), so the two modes stay
consistent with the same canvas.

### How the build applies it

`duo_aspect.install_res` (`dm/tools/duo_aspect.py:78`) asserts two words at an offset
and rewrites them, so the four sites are carried by four `duo/research/res.tsv` rows: each row's
`old_w/new_w` is the size immediate and its `old_h/new_h` is the **neighbouring
instruction, unchanged** (`0xea9330 csel`, `0xeaa740 add`, `0xeabdd0 add`,
`0xea9308 mov w26`). The assert therefore still catches a different build, and only the
intended word changes — verified by applying the rows to the original image: the four
words decode as `mov w21, #0x384`, `mov w8, #0x546`, `mov w2, #0x546`, `mov w2, #0x546`.

The dead row from §4 is gone. One cosmetic wart: `install_res` prints the two words as
decimal "render size 1384154888x445166261" in the build log. Printing them in hex when
they are not plausible sizes is a one-line change to `duo_aspect.install_res`; it does
not affect the patch.

## 7. Verification on device

1. `[nvn] WindowInitialize swap chain 3 textures, interval 1, first 1920x1350 format 0x…`
   (`dm/gfx/nvn/hle_nvn.c:1290`). Before the patch this line says `1920x1080`. The texture
   size is the same in both operation modes (it is the hard-coded pair), so this line is
   the direct proof that the patch took: if it still says 1080, the rows were not applied.
2. `present fill (DM_PRESENT_FILL): …` (`dm/gfx/nvn/nvn_mtl.m:11126`) and the viewport
   from `present_viewport` (`nvn_mtl.m:11118`): with the canvas at 1.4222 and the
   drawable at 1.4215 the ratio difference is 0.05 %, under the 1 % rule at
   `nvn_mtl.m:11129`, so the whole canvas is used with no bars — and now with **no
   anisotropy** either (2853/1920 = 1.486, 2007/1350 = 1.487). `DM_PRESENT_FILL=stretch`
   can stay (it becomes a no-op); leaving it unset is equally fine and is the honest
   setting to test, because it proves the picture's own ratio now matches the screen.
3. Visual: the world is no longer horizontally squeezed (the present's old 0.8
   compression is gone because there is no ratio difference left to compress), and the
   frame shows 25 % more vertical world. The HUD, laid out against the same canvas, is
   undistorted.

## 8. Residual risk

The camera's projection is not in this binary as an aspect value (§5), so the patch
assumes it is derived from the canvas/render size. If after the patch the world is still
squeezed while the log shows 1920x1350, then the engine has a third size source I did
not find — the next places to look, in order:

* the per-view rect at `renderer+0x7e8` fed to `nvnCommandBufferSetViewport`
  (`0xea8400`, single call site `0xea7be8`); its writer was not located (the only
  writes in that range are the zeroing loop at `0xeaf72c`);
* the view object `[renderer+0x7d8]` whose floats at `+0x44/+0x48/+0x4c` are pushed by
  `0xea8230`;
* the game's own blit from its render target into the swap chain (the engine has a
  second 1920x1080 texture builder at `0xeaa734`, whose result is used at `0xeaa2f0`).

## 9. Reproducing the evidence

```sh
python3 dm/tools/nso.py <ExeFS>/main /tmp/sp_main.orig.bin   # needs lz4
python3 dm/tools/sdis.py /tmp/sp_main.orig.bin 0xeaa6f0 40    # SetSize2D site A
python3 dm/tools/sdis.py /tmp/sp_main.orig.bin 0xeabd80 40    # SetSize2D site B
python3 dm/tools/sdis.py /tmp/sp_main.orig.bin 0xea9300 20    # display size decision
python3 dm/tools/sdis.py /tmp/sp_main.orig.bin 0xeabcf0 70    # swap-chain builder
```

The proc-table global was resolved from the `R_AARCH64_RELATIVE` entries at
`DT_RELA = 0xfa7040`, size `0x33c348`, entry `0x18`.
