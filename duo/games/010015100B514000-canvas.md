# Super Mario Bros. Wonder — the Duo canvas lever

Build `cd6e42aee7934f4d8393cd43893ae25e` (v0, `main` at
`/path/to/work/010015100B514000_build/extract/v0/ExeFS/main`).
All offsets below are **image offsets** (text `0x0..0x2012880`, ro at `0x2013000`
size `0x11f5328`, data at `0x3209000` size `0x393c28`, bss `0xa83d8`), i.e. what
`patch_nso.py` rewrites and what `duo/research/res.tsv` numbers.

## 0. The answer, in one line

The window's swap-chain textures are sized from an **int** pair that `nnMain`
builds on its stack and hands to the agl display; the height word is the literal
`mov w8, #0x438` at `0x5a49d0`. It is now a row in `duo/research/res.tsv`:

| offset | original word | new word | meaning |
|---|---|---|---|
| `0x5a49d0` | `0x52808708` `mov w8, #0x438` (1080) | `0x5280a8c8` `mov w8, #0x546` (1350) | display/canvas height 1080 → 1350 |

neighbour (asserted, never written) `0x5a49d4` = `0xb81a03a8`
`stur w8, [x29, #-0x60]`.

The previous row `0x9030f0` (`movk x8, #0x4487, lsl #48`, the float half of a
`{1920.0f, 1080.0f}` pair) is **not** on this path: it is device-proven not to
change the window (the log still said `first 1920x1080`). It is left in place —
it writes a different record (see §5, alternates) — but it is not the canvas.

## 1. The call chain, end to end (all static, every link resolved)

### 1.1 `nnMain` builds the display config block (int 1920 / int 1080)

`nnMain` is `0x5a48d0` (entry stub `b #0x5a48e0`). It puts a 0x50-byte config
block on its stack at `x29-0x78` (`0x5a4948 sub x19, x29, #0x78`), the same block
it later passes to the display constructor:

```
0x5a49bc  mov  x8, #0x3f800000          ; 1.0f
0x5a49c4  movk x8, #0x780, lsl #32      ; -> 0x00000780_3f800000
0x5a49cc  stur x8, [x29, #-0x68]        ; cfg+0x10 = 1.0f, cfg+0x14 = 1920   (width)
0x5a49d0  mov  w8, #0x438               ; 1080                              (height)
0x5a49d4  stur w8, [x29, #-0x60]        ; cfg+0x18 = 1080
```

`0x5a49cc` and `0x5a49d4` are the **only** stores to `[x29,#-0x68]` /
`[x29,#-0x60]` anywhere in `nnMain` (checked instruction by instruction over
`0x5a48e0..0x5a4ac8`), so `cfg+0x14`/`cfg+0x18` hold exactly 1920/1080 when the
display is constructed.

### 1.2 The display object copies the block to `display+0x88`

```
0x5a4a38  mov  w0, #0x2a8               ; the display object (0x2a8 bytes)
0x5a4a44  bl   #0x271d0                 ; operator new
0x5a4a48  sub  x1, x29, #0x78           ; x1 = cfg
0x5a4a50  bl   #0x5a50b8                ; display ctor
0x5a4a54  adrp x8, #0x34f0000 / add #0xf78 ; vptr 0x34f0f78
0x5a4a5c  str  x8, [x19]
```

`0x5a50b8` (derived ctor) calls the base constructor `0x5a5a38` at `0x5a50d0`
with `x0` = display, `x1` = cfg. The base constructor copies the block:

```
0x5a5a9c  str  x8, [x0], #0x88          ; x8 = 0x34f5720, vptr of the +0x88 subobject
0x5a5aa0  mov  w2, #0x50
0x5a5aa4  bl   memcpy                   ; memcpy(display+0x88, cfg, 0x50)
```

so **`display+0x9c` = 1920** (`0x88+0x14`) and **`display+0xa0` = 1080**
(`0x88+0x18`). Neither `0x5a50b8` nor `0x5a5a38` writes `+0x9c`/`+0xa0` again.

The device log cross-checks this block layout through two fields that are *not*
the size: `display+0x88` (the present interval, `0x5a7df4`) is `cfg+0`'s low byte,
which nnMain sets to 1 at `0x5a49b0`/`0x5a49b4`/`0x5a49b8`; and `display+0xa5`
(the extra-texture flag, `0x5a7e0c`) is `cfg+0x1d`, set to 1 by
`0x5a498c stur w8, [x19, #0x1d]` (`x19 = x29-0x78`). The log says `3 textures,
interval 1`, i.e. both bytes are where this mapping says they are — and the height
is the word at `cfg+0x18`, the one the row rewrites.

The third argument of the display init is a *different* pair: `0x5a4aa8`
`mov x8, #0x44a00000` / `0x5a4ab4 movk x8, #0x4434, lsl #48` =
`{1280.0f, 720.0f}`, handed in `x3` at `0x5a4ac4` and kept at `display+0xf8`
(`0x5a79ac str x8, [x19, #0xf8]`). That is the handheld/native-window pair, not
the swap chain (§5).

### 1.3 The display init builds the window record and copies the size into it

`0x5a7908` is the display init: its only caller is `0x5a4ac4` (nnMain), and it is
the only caller of `nn::vi::Initialize` and `nn::vi::CreateLayer` in Wonder, so
every window goes through it. After the vi bring-up it allocates a 0x70-byte
window record, gives it the vtable at `0x34f61a8`, and fills it:

```
0x5a7d78  mov  w1, #0x70                ; the window record
0x5a7d90  adrp x8, #0x34f6000 / add #0x1a8 ; vptr 0x34f61a8
0x5a7d9c  stp  x8, xzr, [x0]
0x5a7dd0  str  x0, [x19, #0x140]        ; display+0x140 = the record
0x5a7dd8  bl   nn::vi::GetNativeWindow
0x5a7de4  str  x9, [x8, #0x50]          ; record+0x50 = native window
0x5a7df4  strb w8, [x9, #0x58]          ; record+0x58 = present interval (display+0x88 byte)
0x5a7e24  strb w9, [x8, #0x59]          ; record+0x59 = 2 + (display+0xa5 != 0) textures
```

then, immediately before the virtual call:

```
0x5a7e28  ldp  s0, s1, [x19, #0x9c]     ; s0 = display+0x9c (1920), s1 = display+0xa0 (1080)
0x5a7e30  ucvtf s1, s1                  ; height
0x5a7e38  ucvtf s0, s0                  ; width
0x5a7e3c  str  s1, [x0, #0xc]           ; record+0xc  = height float
0x5a7e40  str  s0, [x0, #8]             ; record+8   = width float
0x5a7e44  ldr  x8, [x8, #0x10]
0x5a7e48  blr  x8                       ; vtable slot +0x10 of 0x34f61a8
```

`0x34f61a8 + 0x10` = `0x34f61b8`; that slot's `R_AARCH64_RELATIVE` addend is
**`0x978a2c`**. The vtable base `0x34f61a8` is stored by exactly one instruction
pair in the whole image (`0x5a7d90`/`0x5a7d94`, the only `adrp`+`add #0x1a8` to
`0x34f6000`), so this record — and therefore this one call — is the only user of
the builder.

### 1.4 The builder (`0x978a2c`) feeds `nvnTextureBuilderSetSize2D`

```
0x978a4c  ldp  s0, s1, [x0, #8]         ; s0 = record+8 (width), s1 = record+0xc (height)
0x978a60  fcvtzu w24, s1                ; height
0x978a64  fcvtzu w8, s0                 ; width -> [sp,#0xc]
0x978a94  mov  w23, w24                 ; w23 = height
0x978a98  ldr  w24, [sp, #0xc]          ; w24 = width
...
0x978ab4  ldr  x8, [x8, #0x268]         ; nvnTextureBuilderSetDevice   (0x35ad268)
0x978ad0  ldr  x8, [x8, #0x270]         ; nvnTextureBuilderSetDefaults (0x35ad270)
0x978ae0  ldr  x8, [x8, #0x2a8]         ; nvnTextureBuilderSetSize2D  (0x35ad2a8)
0x978ae4  mov  w1, w24                  ; width
0x978ae8  mov  w2, w23                  ; height
0x978aec  blr  x8
0x978afc  SetTarget(1), 0x978b14 SetFormat(record+0x14), 0x978b28 SetFlags(1)
0x978b38  GetStorageSize, 0x978b4c GetStorageAlignment
```

The loop (`0x978aa8..0x978b7c`) runs once per swap-chain texture
(`record+0x59`). A memory pool is then built over the summed storage
(`0x978b8c..0x978bf0`: `nvnMemoryPoolBuilderSetDefaults/SetDevice/SetFlags(0x21)/
SetStorage`, `nvnMemoryPoolInitialize`), each texture is created with
`nvnTextureInitialize` (`0x978cd4`, slot `0x35ad438`) and stored at
`record+0x38` (`0x978c24 add x20, x19, #0x38`; `0x978cd8 str x0, [x20, x23, lsl #3]`),
and finally the window builder runs:

```
0x978cf8  nvnSyncInitialize(record+0x28, device)          (slot 0x35add98)
0x978d28  nvnWindowBuilderSetDefaults                     (0x35acfd8)
0x978d44  nvnWindowBuilderSetDevice                       (0x35acfd0)
0x978d58  nvnWindowBuilderSetNativeWindow(record+0x50)    (0x35acfe0)
0x978d6c  nvnWindowBuilderSetTextures(record+0x59, record+0x38)  (0x35acfe8)
0x978d84  nvnWindowBuilderSetNumActiveTextures            (0x35acff8)
0x978d98  nvnWindowBuilderSetPresentInterval(record+0x58) (0x35acff0)
0x978dac  nvnWindowInitialize(record+0x20, builder)       (0x35ad030)
0x978dc4  nvnWindowAcquireTexture(record+0x20, record+0x28, record+0x30)
```

So: **`0x5a49d0` (1080) → cfg+0x18 → memcpy at `0x5a5aa4` → `display+0xa0` →
`ldp s0,s1,[x19,#0x9c]` + `ucvtf` at `0x5a7e28` → `record+0xc` →
`fcvtzu` at `0x978a60` → `nvnTextureBuilderSetSize2D` at `0x978aec`** → the first
swap-chain texture the host logs.

## 2. Why the 16:9 constant is not the lever, and why `0x9030f0` failed

`duo/research/games.tsv` has no aspect row for this build yet; the 16:9 float exists in
rodata and would be the camera lever. The canvas lever is preferred because it
removes the present stretch instead of compensating for it.

The old row patched the `{1920.0f, 1080.0f}` pair built by `0x9030e8`/`0x9030f0`
and stored at `+0x44` of a *different* record (vtable `0x346b220`) in the graphics
bring-up at `0x9030c0`. The device log still said `first 1920x1080`, which is now
explained: that record is not the one the window record is built from, and no
instruction on the path in §1 reads it. The window's numbers never leave integer
form until `0x5a7e28`.

## 3. The patch

Width stays 1920; height becomes 1350 (1.42222 against the Duo's
2853x2007 = 1.42152 — 0.05 % off, `duo/DESIGN.md`'s tolerance).

`0x5a49d0` is a `movz` (32-bit), so 1350 = `0x546` fits the immediate field and
the instruction stays valid: `0x5280a8c8`. The row asserts both the `movz` and the
next instruction (`0x5a49d4` `stur w8, [x29, #-0x60]`) before writing, so a
different build fails the build rather than producing a half-patched image.

Nothing else changes: the same int pair is also converted into
`display+0x108`/`+0x10c` at `0x5a79dc`/`0x5a79e4`, so anything that reads the
display's own size floats follows the patch too (that mirror is not needed for the
swap chain — the record copy at `0x5a7e3c` is independent of it).

## 4. Expected device log

`dm/gfx/nvn/hle_nvn.c:1290` prints the first swap-chain texture:

```
[nvn] WindowInitialize swap chain 3 textures, interval 1, first 1920x1350 format 0x…
```

(`3` = `record+0x59` = 2 + `[display+0xa5]`, `1` = `record+0x58` = `[display+0x88]`;
both unchanged by the row. The format is `record+0x14`, likewise unchanged.)

Before the patch the same line says `first 1920x1080`. If it still says
`1920x1080` after this row, the display being initialised is not the one nnMain
creates at `0x5a4a44` — check `dm/gfx/nvn/hle_nvn.c`'s own `WindowInitialize`
callers before looking further; the static chain above has no other user of
`0x978a2c` or of the `0x34f61a8` vtable.

## 5. Alternates, with exact addresses and why they were not chosen

| address | instruction | why not |
|---|---|---|
| `0x5a49c4` | `movk x8, #0x780, lsl #32` | the **width** half of the same pair (1920); the Duo keeps 1920 wide. The height is a separate `movz`, which is what makes one word enough. |
| `0x5a49d4` | `stur w8, [x29, #-0x60]` | the store, not a constant: no 1350 encoding exists in it. It is the row's neighbour check. |
| `0x5a4ab4` | `movk x8, #0x4434, lsl #48` | makes the third argument `{1280.0f, 720.0f}`; that pair lands at `display+0xf8` (`0x5a79ac`) and is never read by the window record or the builder. |
| `0x9035f4` | `movk x8, #0x4434, lsl #48` | the handheld `{1280.0f, 720.0f}` pair in the graphics bring-up; same reason as above (different record, different field). |
| `0x9030f0` | `movk x8, #0x4487, lsl #48` | the row that was already here: `{1920.0f, 1080.0f}` at `+0x44` of the record with vtable `0x346b220`; device-proven not to reach the window. Kept in `duo/research/res.tsv` (it may be a render-size pair of that record) but it is not the canvas. |
| `0x5a7e3c` / `0x5a7e40` | `str s1, [x0, #0xc]` / `str s0, [x0, #8]` | the copy of the display pair into the record. The values come from registers (`ucvtf`), so there is no constant to rewrite; patching the source ints is the same change one step earlier. |
| `0x978a60` / `0x978a64` | `fcvtzu w24, s1` / `fcvtzu w8, s0` | conversions, not constants. |
| `0x978ae0` / `0x978aec` | `ldr x8,[x8,#0x2a8]` / `blr x8` | the `nvnTextureBuilderSetSize2D` call itself: it takes the size in `w1`/`w2` from the record; there is no immediate here. |

## 6. Present and what to look for visually

With the canvas at 1.4222 and the drawable at 1.4215 the ratio difference is
0.05 %, under the 1 % rule at `nvn_mtl.m:11129`, so the whole canvas is used with
no bars and no anisotropy (`2853/1920 = 1.486`, `2007/1350 = 1.487`).
`DM_PRESENT_FILL=stretch` becomes a no-op; leaving it unset is the honest test.

Expected picture: 25 % more vertical world, no horizontal squeeze.
