# Burnout Paradise Remastered — the camera projection aspect

Build `74570fa2709ed714006cd65c42a97dc6` (v0), `main` at
`/path/to/work/0100DBF01000A000_build/extract/v0/ExeFS/main`.
Image layout (image offsets = file offsets of the decoded image): text `0..0x967040`,
rodata `0x968000..0xcd37b8`, data `0xcd4000..0x11fad08`, bss `0x10c22f8`.

## 1. Answer

The camera's projection aspect is **not** the rodata `1.7777778` this build is registered
with. Criterion's engine stores the aspect as a *field of the camera/lens object* (`+0x158`),
feeds it from a **data-segment global** (`0xd6bd18`, initial content `0x3FE38E39`) that the
display init writes from the screen-size globals at boot, and turns it into the projection
matrix through the horizontal FOV. Two instructions carry the game's 16:9 into that camera
object and are the patch sites:

| site | instruction | encoding | what it feeds |
|---|---|---|---|
| `0x13d2c` | `ldr s1, [x8, #0x614]` | `0xbd461501` | default-camera setup `0x13d20`: aspect → camera `+0x158` |
| `0x1610ac` | `ldr s10, [x8]` | `0xbd40010a` | camera lens `0x160f80`: aspect → `+0x158` → fovH → projection matrix |

Both are `ldr s<d>,[x<n>,#imm]` (the registry's constant-stub form), so the row is
`0x13d2c,0x1610ac` with no constant. `0xaab614` (the previously registered constant) is only
read by an *intermediate* pass that the same function overwrites, and by the letterbox logic
that must keep comparing against 16:9; see §4.

## 2. The chain

### 2.1 The screen size (documented in `0100DBF01000A000-canvas.md`)

`0x1ad70` (from `0x116a28`) queries `nn::oe::GetOperationMode` and stores
`*0x11fcfc0 = 1920` / `*0x11fcfc8 = 1080` (console) or `1280/720` (handheld), through the GOT
slots `0x11e29f8` / `0x11e2a00`.

### 2.2 The aspect getter — `0x1b300` / `0x1b320`

```
0x1b300  adrp x8,#0x11e2000 ; ldr x8,[x8,#0xa68]   ; override index (bss, 0 by default)
0x1b308  ldr  w8,[x8]
0x1b30c  cbz  w8,#0x1b320                            ; 0 → compute it
0x1b310  adrp x9,#0x11e2000 ; ldr x9,[x9,#0xbb8]    ; a table of ratios (bss)
0x1b318  ldr  s0,[x9,x8,lsl #2]                      ; override path
0x1b31c  ret
0x1b320  adrp x8,#0x11e2000 ; ldr x8,[x8,#0x9f8]    ; *0x11fcfc0  width
0x1b328  ldr  s0,[x8]
0x1b32c  adrp x8,#0x11e2000 ; ldr x8,[x8,#0xa00]    ; *0x11fcfc8  height
0x1b334  ldr  s1,[x8]
0x1b338  scvtf s0,s0
0x1b33c  scvtf s1,s1
0x1b340  fdiv s0,s0,s1                               ; screen aspect == 1920/1080 == 16:9
0x1b344  ret
```

Its callers (direct `bl 0x1b300`): `0xfa964`, `0xfaaf4`, `0xfab9c` and `0x2d7afc`. It is the
engine-wide "what shape is the screen" value.

### 2.3 Into the render/view configuration

`0x2d7840` (the display/view initialiser, `0x2d7840..0x2d8a60`), called from the display init
`0x2ae4b0` at `0x2ae688` with `x2 = sp+0xc`, does:

```
0x2d7afc  bl 0x1b300                       ; s0 = screen aspect
0x2d7b00  str s0,[x20]                     ; out-param (= sp+0xc in 0x2ae4b0)
0x2d7b04  ... cbz w8 -> skip
0x2d7b24  fmul s0,s0,(float)*(int*)0xd56e6c ; scale, 1 by default
0x2d7b28  str  s0,[x20]
0x2d7b2c  adrp x8,#0x11e2000 ; ldr x8,[x8,#0x940]  ; GOT -> 0xd3a790 (.data, 0x3FE38E39)
0x2d7b34  str  s0,[x8]                     ; engine-global aspect
```

`0x2ae4b0` then reads that float and hands it to the renderer initialiser:

```
0x2ae688  bl 0x2d7840          ; x0=obj+0x580, x1=obj+0xc56230, x2=&sp+0xc, x3=&sp+8
0x2ae718  ldr s0,[sp,#0xc]    ; the aspect
0x2ae728  bl 0x168070          ; x0 = obj+0x785310
```

`0x168070` keeps it in `d8`/`v8` (0x168080 `mov v8.16b,v0.16b`) and forwards it to the
aspect setter at `0x168348`:

```
0x168344  str w20,[x19,#0x2d678]
0x168348  bl  0x15a840          ; x0 = obj+0x785310, s0 = aspect
```

### 2.4 The aspect setter — `0x15a840`

```
0x15a840  ...
0x15a864  adrp x8,#0x11e5000
0x15a868  ldr  x8,[x8,#0x630]     ; GOT 0x11e5630 -> 0xd6bd18 (.data)
0x15a874  str  s0,[x0,#0x2c1c8]   ; the render object's own copy
0x15a878  str  s0,[x8]            ; <<< the global the camera reads (0xd6bd18)
0x15a8a8  bl   0x13d20            ; and a default camera at obj+0xb740
```

Only caller: `0x168348`. Only writer of `0xd6bd18` in the module.

### 2.5 The camera lens — `0x160f80` (the one that builds the projection)

`0x160f80..0x16119c`, called from `0x15f4a8`, `0x167d9c`, `0x17e5a0`, `0x19b9e8`,
`0x2bdffc`, `0x2e7bec`, `0x546f68`, `0x58c09c`, `0x58cd84`, `0x58ce30`, `0x58d84c` (every
camera/lens type in the game):

```
0x160fa8  bl 0x13d20                          ; default camera (fov 90deg, 16:9, 0.1, 1000)
0x161000  ldr s0,[x19,#0x14c] ; *0.5 ; bl tanf (0x965520) ; 1/x -> +0x150
0x16100c  ldr s1,[x8,#0x614]   (16:9 rodata) ; *tan ; bl atan? (0x965530) ; *2 -> +0x140
...
0x1610a0  adrp x8,#0x11e5000
0x1610a4  ldr  x8,[x8,#0x630]                ; GOT -> 0xd6bd18
0x1610ac  ldr  s10,[x8]                       ; <<< THE camera aspect (16:9 today)
0x1610b0  fmul s0,s0,s8                       ; fovV/2
0x1610b4  str  s10,[x19,#0x158]               ; camera aspect field
0x1610b8  bl   0x965520                      ; tan
0x1610bc  str  s0,[x19,#0x154]                ; tan(fovV/2)
0x1610c4  str  s0,[x19,#0x150]                ; 1/tan(fovV/2)
0x1610d4  fmul s0,s10,s0                      ; tan(fovV/2) * aspect
0x1610d8  bl   0x965530                      ; atan
0x1610dc  fadd s0,s0,s0                       ; fovH = 2*atan(tan(fovV/2)*aspect)
0x1610e0  str  s0,[x19,#0x140]
0x1610e8  bl   0x965520 ; 0x1610ec str s0,[x19,#0x148] ; 0x1610f0 1/x -> +0x144
0x1610fc  bl 0x14480                          ; projection matrix
...
0x161168  bl 0x14480   (after near/far are rewritten from 0x11e5670/0x11e5678/0x11e5680)
0x161180  bl 0x14480
```

Field map of the camera object (from `0x13d50`'s stores and `0x14480`'s loads):
`+0x140` fovH, `+0x144` 1/tan(fovH/2), `+0x148` tan(fovH/2), `+0x14c` fovV,
`+0x150` 1/tan(fovV/2), `+0x154` tan(fovV/2), `+0x158` **aspect**, `+0x15c` near, `+0x160` far,
`+0x164..+0x170` depth range (-1,-1,1,1), matrices at `+0x00..+0xb0`.

### 2.6 The projection matrix builder — `0x14480`

```
0x14480  ldr s1,[x0,#0x16c] ; ldr s2,[x0,#0x164]     ; depth range
0x144a0  fmov s0,#2.0 ; fdiv s5,s0,s3                  ; 2/(far-near)
0x144bc  add  x8,x0,#0x150
0x144f0  ld1  {v0.s}[1],[x8]                          ; yscale = 1/tan(fovV/2)
0x1450c  add  x8,x0,#0x144
0x14524  ld1  {v4.s}[0],[x8]                          ; xscale = 1/tan(fovH/2)  <- aspect here
0x14538  ldr s16,[x0,#0x160] ; ldr s7,[x0,#0x15c]      ; far, near
0x14568  stp q2,q0,[x0,#0x40]
0x14598  stp q1,q3,[x0,#0x60]
0x145e8  stp q3,q4,[x0,#0x80]
0x145ec  stp q2,q0,[x0,#0xa0]
0x145f0  ret
```

So the aspect reaches the matrix only through `fovH`/`1/tan(fovH/2)`; the vertical FOV is
preserved and the horizontal narrows — the Crop-equivalent framing the Duo needs while the
canvas stays 1920x1080.

### 2.7 The default camera setup — `0x13d20` → `0x13d50`

`0x13d20` is a 3-word thunk that loads four rodata floats and tail-branches to `0x13d50`:

```
0x13d24  ldr s0,[x8,#0x4fc]   ; 0xaab4fc = 1.5707964  (90 deg fov)
0x13d2c  ldr s1,[x8,#0x614]   ; 0xaab614 = 1.7777778  (aspect)   <<< SITE
0x13d34  ldr s2,[x8,#0x368]   ; 0xaab368 = 0.1        (near)
0x13d3c  ldr s3,[x8,#0x36c]   ; 0xaab36c = 1000.0     (far)
0x13d40  b   0x13d50
0x13d50  mov v8.16b,v1.16b
0x13d88  str s2,[x0,#0x15c]    ; near
0x13d90  ...
0x13da8  str s3,[x0,#0x160]    ; far
0x13db0  str s8,[x0,#0x158]    ; aspect
0x13e10  str s0,[x0,#0x140]    ; fov
0x13ea4  stp q1,q2,[x0,#0x40]  ... matrices (+0x40..+0xb0)
0x13f00  fdiv s1,s1,s8         ; 1/aspect, the fov-H <-> fov-V conversion
0x13f0c  fadd s0,s0,s0 ; 0x13f10 str s0,[x19,#0x14c]
```

`0x13d20` is called directly by `0x160f80` (0x160fa8) and by `0x2bf28`, `0x30154`,
`0x321b8`, `0x15a8a8`, `0x195d18`, `0x1a8dd0`, `0x582244..0x582294`, `0x58c088`, `0x58d834`
(the camera objects and their sub-cameras). Patching `0x13d2c` makes all of them take the
Duo ratio. (`0x13d50` is also entered directly at `0x2c194` with aspect 1.0 and
`0x53d1d8` with caller-computed values — deliberate non-default cameras; left alone.)

## 3. The patch

Both sites are `ldr s<d>,[x<n>,#imm]` (`(w & 0xffc00000) == 0xbd400000`), so
`duo_aspect.install_sites_const` replaces each with `b stub`, and the stub is
`ldr s<d>, <literal>` · `b site+4` · `.float 1.4215247` (the ratio of `DM_DUO_ASPECT`, here
2853:2007 = 1.4215246636771302 = `0x3FB5F485`). The dropped load has no side effect.

Simulated with the real `duo_aspect.install_sites_const` (row sites fed in place of the
tsv, patch area at the module's `PATCH_OFF` = `0x22d0000`):

```
0x13d2c  bd461501 form_ok True   ->  b5f08a14  (b #0x22d0000)
0x1610ac bd40010a form_ok True   ->  d8bb8514  (b #0x22d000c)
0x22d0000  1c000041  ldr s1,  #0x22d0008
0x22d0004  17750f4b  b   #0x13d30        ; back to the instruction after the site
0x22d0008  3fb5f485  .float 1.4215247
0x22d000c  1c00004a  ldr s10, #0x22d0014
0x22d0010  177a4428  b   #0x1610b0
0x22d0014  3fb5f485  .float 1.4215247
ratio (1068889221, 1.4215246636771302)
```

No `nx build --prepare-xcode` run: the row can only be exercised through `duo/research/games.tsv`,
which this investigation must not edit; the mechanics were checked by calling
`install_sites_const` directly against the real module (above). Also note the module is
`FAR == 0` (patch area at ~0x22d0000, 35 MB from both sites, well inside the ±128 MB branch
reach).

## 4. Rejected alternates

* **`0xaab614` (the registered constant, and `0xaf9cf4` / `0xaf9d30`).** `0xaab614` has 7
  readers: `0x13d2c` (default camera, here replaced by the stub), `0x161010` (an
  intermediate `fovH` pass inside `0x160f80` that the `0x1610a4` block recomputes and
  overwrites at `0x1610d4`/`0x1610e0`), `0x1b4cc` (the letterbox logic of `0x1b460`, which
  compares the *drawable* ratio against 16:9, `fcmp s2,s3 ; b.le` — it must keep 16:9 so the
  1920x1080 canvas is still treated as a full 16:9 frame), `0x2b1478` (a scene/room object),
  `0x2d7b50` and `0x2e7d70` (both fed to the screen-fit helper `0x17dc0` together with a
  frame-size table — 2D sizing, not the 3D projection). So the constant patch does not reach
  the final camera matrices and would perturb the letterbox path. `0xaf9cf4`/`0xaf9d30` have
  no `adrp`/literal reference at all (dead copies, one of the three 16:9 words the old scan
  counted).
* **The data copies `0xd6bd18` and `0xd3a790`** (both `0x3FE38E39`). They look like the
  obvious one-word targets, but both are *written at boot*: `0x15a878` stores the aspect the
  display init computed into `0xd6bd18`, and `0x2d7b34` stores it into `0xd3a790`. A static
  word patch is overwritten before the first frame.
* **`0x1b340` (the `fdiv` of width/height).** This is the true source of the ratio and would
  be the analogue of 3D World's camera fdivs; it is `0x1e201800`-form, so a constant stub
  works there too. Not registered: it changes the engine-wide screen ratio, which also feeds
  the 2D/screen-space consumers read through GOT `0x11e2940` (`0x17bcb4`, `0x17d55c`,
  `0x17e018`, `0x194a00`, `0x185dc0`) — HUD/UI layout is the separate second step in
  `duo/design/aspect.md`, and the camera is already fully covered by the two sites above.
  Keep it as the fallback if a camera ever proves to bypass both camera sites.
* **`0x5a2314`, `0x8d5f28` and the other `#0xb0` hits of `duo/tools/find_aspect.py`.** Those
  files' `+0xb0` stores are plain struct-field lerps (`ldr s,[x,#0xb0] ; fsub/fadd ;
  str s,[x0,#0xb0]`), not a sead-style projection struct; Criterion has no sead here. They
  are unrelated to the projection.
* **The canvas rows already in `duo/research/res.tsv`** (`0x1ada8`, `0x1adac`, `0x5ed30c`). They do
  make `0x1b340` return 1920/1350 = 1.4222, so they would work through the chain above, but
  they are the canvas lever the method bans (and they resize the swap chain); the camera
  rows require none of it.

## 5. What was not verified

Behaviour on the device. The static chain above is complete and the stubs install cleanly,
but nobody has run this build with the row on hardware; the verification of
`duo/design/aspect.md` §5 (NCC of a Stretch screenshot against a cropped 1080 frame) is still
to be done. If the world still looks stretched, the next thing to check is whether the
visible camera is one of the `0x13d50` direct callers (0x2c194 / 0x53d1d8) rather than a
`0x160f80` lens, and then the `0x1b340` stub is the remaining lever.

## 6. Reproducing

```sh
python3 dm/tools/nso.py <ExeFS>/main /tmp/bop_main.bin
python3 dm/tools/sdis.py /tmp/bop_main.bin 0x1b320 20      # screen aspect getter
python3 dm/tools/sdis.py /tmp/bop_main.bin 0x160f80 140    # camera lens
python3 dm/tools/sdis.py /tmp/bop_main.bin 0x14480 96      # projection matrices
python3 dm/tools/sdis.py /tmp/bop_main.bin 0x13d20 20      # default camera (site 0x13d2c)
```
