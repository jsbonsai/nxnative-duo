# Luigi's Mansion 3 — the Duo aspect lever (canvas size)

Build `79e5950ffa85acf63e28c9aec051eac2` (v327680, `main` at
`/path/to/work/0100DCA0064A6000_build/extract/v327680/ExeFS/main`).
Offsets are **image offsets** — what `patch_nso.py` rewrites and what `duo/research/res.tsv`
carries: text `0..0x1045f90`, rodata `0x1046000..0x1690fbc`, data `0x1692000..0x18850e0`
(above `0x18850e0` is BSS).

## 0. What the first attempt got wrong (device evidence)

Four rows patching the docked/handheld `csel` of 1920×1080 / 1280×720 (`0x45856c`,
`0x458570`, `0xb7a924`, `0xb7a928`) applied cleanly and changed nothing:

```
[nvn] WindowInitialize swap chain 3 textures, interval 1, first 1920x1080 format 0x38
[nvn] the game sets present interval 1 → 2
```

Those four words feed `0x7c1890(w,h)`, the *post-boot* display-size application. The
swap-chain textures are not built from that call: they are built from the renderer's own
canvas record, and at boot that record still holds its lazily-inlined **default**
(1920×1080). The four rows are kept (they keep the resize path on the same aspect) but
they are not the lever — §3 is.

## 1. What the log line reports

`[nvn] WindowInitialize … first WxH` (`dm/gfx/nvn/hle_nvn.c:1290`) prints the first
swap-chain texture's dimensions, i.e. what the guest passed to the NVN texture builder.

NVN is resolved by name at startup into a proc table based at **`0x1cd4000`** (resolver
body `0xb77e00`…`0xb7a8xx`: `adrp x1,<page>; add x1,x1,#<off>; mov x0,x20; blr x19;
adrp x8,#0x1cd4000; str x0,[x8,#<slot>]`). Relevant slots:

| slot | proc |
|---|---|
| `0x1cd4618` / `0x1cd4620` | `nvnWindowBuilderSetDevice` / `SetDefaults` |
| `0x1cd4628` / `0x1cd4630` | `nvnWindowBuilderSetNativeWindow` / `SetTextures` |
| `0x1cd4678` | `nvnWindowInitialize` |
| `0x1cd46b0` | `nvnWindowSetCrop` |
| `0x1cd48c8` / `0x1cd48d0` | `nvnTextureBuilderSetWidth` / `SetHeight` |
| `0x1cd48e8` | `nvnTextureBuilderSetSize2D` (**never called**) |

## 2. The swap chain is built from one size record

`0x78c0b0` (the renderer's lazy init, `sub sp, sp, #0x160`) picks the canvas record into
`x25` and then builds the three swap-chain textures:

```
0x78c248  ldrb w8,[0x1c8d908]; cmp w8,#1; b.ne 0x78c274   ; "canvas applied?"
0x78c268  adrp x25,#0x1c8d000; add x25,x25,#0x918          ; x25 = the canvas record
…
0x78d80c  ldrh w8,[x25,#0x74]        ; u16 width
0x78d824  ldr  w9,[x25,#0x7c]        ; u16 height (packed into the resource key)
0x78d980  ldr  w9,[x25,#0x74]        ; width  → descriptor +0xa4
0x78d988  strh w9,[sp,#0xa4]
0x78d98c  ldr  w9,[x25,#0x7c]        ; height → descriptor +0xa6
0x78d990  strh w9,[sp,#0xa6]
0x78d994  ldrb w9,[x25,#0x59]; and w9,w9,#0x3f; strb w9,[sp,#0xac]   ; NVN format (0x38)
0x78da00  bl   0xb80320              ; texture definition from that descriptor
0x78da44  bl   0x7cb150              ; render-target pool
0x78da50  str  x0,[0x1ce50f0]        ; swap-chain texture 0
0x78da68  str  x0,[0x1ce50f8]        ; swap-chain texture 1
0x78da80  str  x0,[0x1ce5100]        ; swap-chain texture 2
```

`0xb7ac00` then picks those three up, reads them back with `nvnTextureGetWidth`/`GetHeight`
(`0x1cd4ab0`/`0x1cd4ab8`), and calls `SetDefaults`/`SetDevice`/`SetNativeWindow`/
`SetTextures(builder,3,…)`/`WindowInitialize` — that is the logged line.

The size itself reaches NVN through the descriptor's u16 `+4`/`+6`, set by `0xb81d10` at
creation and read at `0xb81f40`/`0xb81f54` into `nvnTextureBuilderSetWidth`/`SetHeight`.

## 3. The record at `0x1c8d918` — the one lever

Layout (all `u32` unless noted):

| field | meaning | value |
|---|---|---|
| `+0x74` | canvas width (read as u16) | 1920 |
| `+0x7c` | canvas height (read as u16) | 1080 |
| `+0x64`, `+0x6c` | the same pair in the other slot order | 1080, 1920 |
| `+0x59` | NVN format byte (`&0x3f`) | 0x38 |

Two writers:

**(a) the display-size application, `0x7c1890(w0=width, w1=height)`** — this is what the
four `csel` rows feed:

```
0x7c1890  x9 = 0x1c8d918
0x7c1914  fcvtzs w13, s0                 ; round((w/h)*h)
0x7c1928  strb w8(=1),[0x1c8d908]        ; "canvas applied"
0x7c1938  stp w1, w13, [x9, #0x68]
0x7c1940  stp w13, w0, [x9, #0x70]       ; +0x74 = width
0x7c1948  stp w0, w1, [x9, #0x78]        ; +0x7c = height
```

Its only two callers are `0x4585d8` and `0x45d5ac`, both fed by the docked/handheld
`csel` over the `nn::oe::GetOperationMode` byte `0x1cd3944` (import `0x18712f0`, PLT
`0x1044190`, published at `0xb5d3fc`/`0xb5d418`).

**(b) the lazily-inlined default constructor**, which is what the boot path actually
sees. Every copy ends with:

```
mov  x10, #0x78000000780        ; 1920, 1920
mov  x11, #0x438                ; 1080        ← the height constant
movk x11, #0x438, lsl #32
stur x10, [x8, #0x24]           ; +0x74 = 1920
stur x10, [x8, #0x1c]           ; +0x6c = 1920
stur x11, [x8, #0x2c]           ; +0x7c = 1080
stur x11, [x8, #0x14]           ; +0x64 = 1080
```

`x8` is `0x1c8d968`, i.e. record `+0x50`, so `+0x24`/`+0x2c` are `+0x74`/`+0x7c`. The
constructor is **inlined at 81 sites** (`0x67cc0`, `0x68ab0`, … `0x7c1a3c` … `0x78e254`;
two of them reach the record through `mov x9, x8`), guarded by the usual once-flag;
whichever site runs first writes 1920×1080. One further copy, `0x78e178`, is *not* this
record — it builds the alternate object at `0x1bd2f10` — and is deliberately left alone.

Why (b) wins at boot: the renderer init takes its "canvas applied?" branch on
`[0x1c8d908]`, which the display-size application sets — so the application runs first,
but its *input* is the record itself (`0x45d420`: `ldr w20,[x22]; ldr w21,[x22,#4]`), i.e.
it re-applies whatever the constructor already wrote. With the `csel` patched the record
stays 1080 because the `csel` never reaches it on this path. That is exactly what the
device log shows.

## 4. The patch

Heights only; widths stay 1920 so the horizontal pixel scale is 1:1.

* **81 rows**: `mov x11, #0x438` → `mov x11, #0x546` (`0xd280870b` → `0xd280a8cb`) at every
  inlined copy of the default constructor — the canvas default becomes 1920×1350, so the
  swap chain, the render targets and the aspect getter all start at 1.4222.
* **4 rows** (kept from the first attempt): the two `csel` sites, so the post-boot resize
  path agrees — `0x45856c`/`0xb7a924` 1080→1350 and `0x458570`/`0xb7a928` 720→900.

1920×1350 = 1.42222 against the Duo's 2853×2007 = 1.42152 (0.05 % off, the tolerance
`duo/DESIGN.md` accepts); the handheld branch stays on the same aspect at 1280×900.

The 16:9 constant row this build already has in `duo/research/games.tsv` (`0x13c96fc`) stays valid
and is complementary: the canvas now carries the Duo ratio, and the projection aspect is
then set to the drawable's ratio, 0.05 % away.

## 5. Verification on device

1. `[nvn] WindowInitialize swap chain 3 textures, interval 1, first 1920x1350 format 0x38`
   (`dm/gfx/nvn/hle_nvn.c:1290`). The size is the record pair read at `0x78d980`/`0x78d98c`,
   so this line is the direct proof that the constructor rows took. `format 0x38` must not
   change (it comes from `[0x1c8d918+0x59]`).
2. `[nvn] WindowCrop 0,0 1920x1350` — written by the same record through `0xb7e3d0` →
   `nvnWindowSetCrop`. It must agree with the texture size.
3. Visual: with canvas and drawable both at ~1.4222 the present ratio check
   (`nvn_mtl.m:11129`, 1 % rule) passes, the whole canvas is used with no bars, and the
   frame shows 25 % more vertical world without a horizontal squeeze.

## 6. Residual risk

If the log still says `1920x1080`, the running constructor copy is not among the 82 and the
thing to watch is the write pair itself:

* `0x78d98c  ldr w9,[x25,#0x7c]` / `0x78d990 strh w9,[sp,#0xa6]` — the height that reaches
  the swap-chain texture definition. Breakpoint there: `w9` is the canvas height.
* `0x7c1948  stp w0, w1, [x9, #0x78]` — the display-size application writing `+0x78`/`+0x7c`.
* `0x67cc0` / `0x7c1a3c` — two of the constructor copies; whichever one executes is the
  first user of the record at boot.

If `w9` at `0x78d990` reads 1350 but the log still shows 1080, then the three textures were
built from a *different* descriptor path and the next place to look is `0xb81d10`'s callers
(`0xb80634`, `0xb8075c`, `0x446de0`, `0x478f6c`, `0x48493c`…`0x484a34`).

## 7. Reproducing the evidence

```sh
python3 dm/tools/nso.py <ExeFS>/main /tmp/lm3_main.bin
python3 dm/tools/sdis.py /tmp/lm3_main.bin 0x78c0b0 1200   # renderer init: record → swap chain
python3 dm/tools/sdis.py /tmp/lm3_main.bin 0x78d980 10     # width/height loads
python3 dm/tools/sdis.py /tmp/lm3_main.bin 0x7c1890 60     # display-size application
python3 dm/tools/sdis.py /tmp/lm3_main.bin 0x67cb0 20      # default constructor (one of 82)
python3 dm/tools/sdis.py /tmp/lm3_main.bin 0xb81f20 20     # SetWidth/SetHeight from the descriptor
```

Proc names come from the resolver body `0xb77e00`…`0xb7a8xx`; imported Horizon symbols
(`nn::oe::GetOperationMode`, `nvnBootstrapLoader`, …) come from `DT_JMPREL` (tag 23) in the
dynamic section.
