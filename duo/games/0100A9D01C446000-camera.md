# DRAGON QUEST VII Reimagined — the camera projection aspect

Build `ab06020960edd8285b7ff5fad2e3224b` (v65536), `main` at
`/path/to/work/0100A9D01C446000_build/extract/v65536/ExeFS/main`.
Image offsets: text `0..0x4f8e9f0`, rodata `0x4f8f000..0x5819000`, data `0x5819000..0x63bb748`.

Engine: **Unreal Engine 4.27.2** — `++UE4+Release-4.27-CL-0` (UTF-16 @ `0x5408fb8`),
`SDK MW+EpicGames+UnrealEngine-4_27_2` (data `0x58184e2`), and the 4.27 reflection names
`bConstrainAspectRatio`, `EAspectRatioAxisConstraint`, `MinimalViewInfo`, `SceneViewport`
in the data segment. The imports are the stock SDK set (`DT_JMPREL`, 717 entries); `tanf`
is PLT stub `0x4f8bfc0`, `tan` `0x4f8c0e0`.

**Result: the camera aspect *is* in native code and it is a viewport-rect division.** The
projection of every view goes through the 4.27 `FMinimalViewInfo::CalculateProjectionMatrixGivenView`
body, which divides `UnconstrainedViewRect.Width()` by `.Height()` (or the inverse, by
`EAspectRatioAxisConstraint`) and feeds the two scale elements of the projection matrix. The
registry row below is nevertheless `-`/`-`, because the *live* division produces the
**inverse** aspect and the current stub (`dm/tools/duo_aspect.py: const_stub`) always writes
`DM_DUO_ASPECT` itself — see §2. The old 16:9 const row is wrong for this game and is dropped.

## 1. The chain

### 1.1 The destination is an `FSceneViewProjectionData`

```
1038104  ldp      w8, w9, [x19, #0x98]     ; X2, Y2
1038108  ldp      w11, w12, [x19, #0x90]   ; X1, Y1
103810c  sub      w8, w8, w11              ; Width  = X2 - X1
1038110  sub      w9, w9, w12              ; Height = Y2 - Y1
...
1037e5c  str      s0,  [x19, #0x64]        ; ProjectionMatrix.M[1][1]
1037e68  str      s10, [x19, #0x50]        ; ProjectionMatrix.M[0][0]
1037e6c  str      wzr, [x19, #0x60]
1037e70  str      xzr, [x19, #0x58]
1037e74  str      wzr, [x19, #0x54]
1037e78  stp      d9, d2,  [x19, #0x68]
1037e80  stp      d1, d9,  [x19, #0x78]
1037e7c  str      d4,  [x19, #0x88]
```

That is exactly UE4.27's layout, and the only structure with a 16-byte `FIntRect` at `+0x90`
*and* a 64-byte `FMatrix` at `+0x50` is
`FSceneViewProjectionData { FVector ViewOrigin; FMatrix ViewRotationMatrix (+0x10);
FMatrix ProjectionMatrix (+0x50); FIntRect UnconstrainedViewRect (+0x90);
FIntRect ConstrainedViewRect (+0xa0); }`. The matrix is written in place (`M[0][0]` at `+0x50`,
`M[1][1]` at `+0x64`, i.e. row 1 of a 16-byte row), so this function *is* the projection
builder — not a consumer of one.

### 1.2 The FOV side of the matrix

```
10384dc  ldr      s0, [sp, #0xe8]          ; ViewInfo.FOV (degrees), stack copy of FMinimalViewInfo
10384e0  fmov     s1, #0.50000000
10384e8  ldr      s2, [x8, #0xe5c]         ; 0x3c8efa35 = 0.0174532924f (deg2rad)
10384f0  fmul     s1, s0, s1               ; FOV * 0.5
10384f4  fmul     s4, s1, s2               ; = FOV * PI / 360   (half FOV, radians)
1038500  fcmp     s0, s2                   ; clamp: FOV <= 0.001f (0x5183e54) ...
1038508  fcsel    s0, s0, s4, ls
103850c  bl       #0x4f8bfc0              ; tanf()
1038180  fmov     s8, s0                   ; s8 = tan(half FOV)
```

The other branch uses the same conversion inline (`0x1038138 mov w8,#0x43b40000` = 360.0f,
`0x103813c fmul s1,s0,PI`, `0x1038148 fdiv s1,s1,s2`), i.e. `HalfFOV = FOV*PI/360` as in the
4.27 source. The fallback constant on the low side is `8.726646e-6` (`0x51836f8`), the `0.001f`
guard is `0x5183e54` — both 4.27 `SetupProjection`/`CalculateProjectionMatrix` clamps.

### 1.3 The two aspect divisions

```
10380fc  ldrb     w10, [x22, #0x94]        ; EAspectRatioAxisConstraint (passed in by the caller)
1038100  cmp      w10, #2                  ; MajorAxisFOV ?
1038114  ccmp     w8, w9, #4, eq           ; ... and W > H ?
1038118  b.gt     #0x1038124               ;   yes -> the "maintain X" branch
103811c  cmp      w10, #1                  ; MaintainXFOV ?
1038120  b.ne     #0x10384a4               ;   no  -> the "maintain Y" branch

; ---- branch "maintain X" (MaintainXFOV, or MajorAxisFOV with Width>Height) ----
1038124  scvtf    s0, w8                   ; Width
1038128  fmov     s10, #1.00000000
103812c  scvtf    s1, w9                   ; Height
1038130  fdiv     s11, s0, s1              ; <<< SITE A: aspect = Width / Height

; ---- branch "maintain Y" (MaintainYFOV = 0, the UE4 default) ----
10384a4  ldrb     w10, [sp, #0x101]
10384a8  cmp      w10, #1
10384ac  b.eq     #0x1038124
10384b0  scvtf    s0, w9                   ; Height
10384b4  fmov     s11, #1.00000000
10384b8  scvtf    s1, w8                   ; Width
10384bc  fdiv     s10, s0, s1              ; <<< SITE B: inv aspect = Height / Width

; ---- common tail (both branches) ----
10381ac  fdiv     s0, s11, s8              ; M[1][1] = (W/H or 1) / tan(halfFOV)
10381b0  fdiv     s10, s10, s8             ; M[0][0] = (1 or H/W) / tan(halfFOV)
```

So on a 1920x1080 rect both branches yield the same matrix `M00/M11 = 1080/1920 = 0.5625`
(= 1/1.7778); they differ only in which side the FOV degrees belong to:

| constraint | live site | value it produces | M00 | M11 |
|---|---|---|---|---|
| `AspectRatio_MaintainXFOV` (1), or `MajorAxisFOV` (2) with W>H | `0x1038130` | W/H = 1.7778 | 1/tan | (W/H)/tan |
| `AspectRatio_MaintainYFOV` (0) — **UE4's default** | `0x10384bc` | H/W = 0.5625 | (H/W)/tan | 1/tan |

`EAspectRatioAxisConstraint` is `APlayerCameraManager::AspectRatioAxisConstraint`. UE 4.27
initialises it to `AspectRatio_MaintainYFOV` (enum value 0) in the class defaults, so unless
this title overrides that property (C++ or Blueprint), **the live path is site B,
`0x10384bc`**. The value is data (CDO / Blueprint default), not code, so it cannot be read
out of `main`; the table above lists both branches so one device run tells them apart.

## 2. What the Duo needs (the arithmetic the rewriter must respect)

On the Duo the canvas stays 1920x1080 and the front end stretches it to 2853x2007. For a
world feature to keep its shape, the canvas projection must satisfy
`M00/M11 = 1080/1350 = 1/1.4215247 = 0.7034703` instead of `0.5625`.

* **Site A (`0x1038130`, W/H)** — substituting `1.4215247` gives `M00/M11 = 1/1.4215247`:
  **correct**, and it is exactly what `const_stub` writes.
* **Site B (`0x10384bc`, H/W)** — the register must receive `1/1.4215247 = 0.7034703`, **not**
  `1.4215247`. Substituting the ratio there gives `M00/M11 = 1.4215247` and a picture ~2.0x
  too wide (1.4215^2 on screen), i.e. it inverts the bug instead of fixing it.

`dm/tools/duo_aspect.py: ratio_bits()` always builds the site literal from `DM_DUO_ASPECT`,
so the live site cannot be expressed today. Two ways forward, both outside this ticket:

1. add a reciprocal form to `duo/research/games.tsv` (e.g. `!0x10384bc`), or
2. build this game with `DM_DUO_ASPECT=2007:2853` and the plain site `0x10384bc`
   (2007/2853 = 0.70347) — correct, but it makes the row depend on the build environment.

The registry row is therefore left at `-`/`-`: a build of the current row list would either be
a silent no-op (site A, wrong branch) or a visibly wrong patch (site B with the default env).
I did **not** run `nx build --prepare-xcode`, so there are no rewrite lines or `main.cuts.tsv`
lines to quote.

## 3. The 16:9 rodata constant `0x5183ddc` is UI, not the camera — drop it

Every reader of `0x5183ddc` (found with `adrp`+`ldr s`): `0x127b08`, `0x18b170`, `0x3c8670`,
`0x54f558`, `0x630528` (`0x630508` in the same basic block). All five are the same shape —
the Slate/UMG *design-resolution* scale for a 3840x2160 reference:

```
127afc  ldp      s0, s1, [x8]             ; viewport width, height
127b00  fdiv     s2, s0, s1               ; ratio
127b04  adrp     x8, #0x5183000
127b08  ldr      s3, [x8, #0xddc]         ; 1.7777778f  << the registered constant
127b0c  fcmp     s2, s3
127b10  b.gt     #0x127e34                ; ratio > 16:9 -> scale = 2160.0f (0x45070000) / height
127b14  mov      w8, #0x45700000          ; else        -> scale = 3840.0f / width
```

(`0x18b170`, `0x3c8670`, `0x54f558` are byte-for-byte the same test; `0x630508`/`0x630528`
convert a coordinate *by* the constant: `fdiv` / `fmul` + `fcvtzs`. `0x5183ddc` is also the
same dword as the 0x51836xx block that holds the UI clamps.) None of the five reaches an
`FMatrix`, a `tanf` call, or `FSceneViewProjectionData+0x50`. The const row in
`duo/research/games.tsv` was never verified on device and this is why: it can only move the HUD/UI
scale, never the 3D projection.

## 5. Reproducing the evidence

```sh
python3 dm/tools/nso.py <ExeFS>/main /tmp/dq7.bin         # text 0..0x4f8e9f0, rodata 0x4f8f000, data 0x5819000
python3 dm/tools/sdis.py /tmp/dq7.bin 0x10380fc 40        # the constraint test
python3 dm/tools/sdis.py /tmp/dq7.bin 0x1038130 12        # SITE A  fdiv s11,s0,s1  (0x1e21180b)
python3 dm/tools/sdis.py /tmp/dq7.bin 0x10384b0 16        # SITE B  fdiv s10,s0,s1  (0x1e21180a)
python3 dm/tools/sdis.py /tmp/dq7.bin 0x10381ac 12        # the two matrix elements
python3 dm/tools/sdis.py /tmp/dq7.bin 0x1037e50 16        # stores into FSceneViewProjectionData
python3 duo/tools/find_aspect.py <ExeFS>/main              # what it does NOT find (see note)
```

`duo/tools/find_aspect.py` does not surface these two sites: it scores by the sead projection
pattern (`str s,[x,#0xb0]`/`#0xac`) and by the 16:9 constant, neither of which Unreal has, and
its `fdiv` scan is unfiltered (37 rows shown of 131,726). The Unreal map needs the
`FSceneViewProjectionData` offsets instead: a `ldp w?,w?,[x?,#0x90]`/`#0x98` rect read, an
`str s?,[x?,#0x50]`, and a `tanf` in the same body.
