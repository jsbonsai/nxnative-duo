# Super Mario 3D World — the UI's 1.25x vertical stretch

Build `891687f016a18f1773d4a88ebf8a973c` (v262144, `main`). All offsets are **image
offsets** (text `0x0..0x9c4a80`, ro `0x9c5000` size `0x8a2ee4`, data `0x1268000` size
`0x1b8e98`, bss `0x731168`) — the numbers `duo/research/res.tsv` and `patch_nso.py` use.

Companion: `duo/games/010028600EBDA000-canvas.md` (the canvas lever, already in `res.tsv`).
This file is the second half: the canvas is 1920x1350 and the **world** is correct, but the
HUD/menus are drawn 1.25x too tall (`1350/1080`), measured on device as the round A and B
button discs being 40x49 px instead of 40x40.

## 0. The short version

The UI is `nn::ui2d` (= NintendoWare lyr) layouts. The game keeps a **UI resolution** in a
6-entry table at `0x13e7c30` and draws every layout into a viewport of exactly that size.
The table's 1920x1080 entries made the layouts' 1080-unit design space cover the 1350-row
canvas, i.e. a 1.25 vertical stretch. The patch raises the height of the four live
`{1920,1080}` entries to 1350, so the UI resolution equals the canvas and layouts draw at
1:1 pixels:

| offset | original | new | entry |
|---|---|---|---|
| `0x13e7c4c` | `0x00000438` (1080) | `0x00000546` (1350) | 0 (`0x13e7c30`) |
| `0x13e7d48` | `0x00000438` | `0x00000546` | 3 (`0x13e7d2c`), selected by bit 0 at `0x8023e0` |
| `0x13e7d9c` | `0x00000438` | `0x00000546` | 4 (`0x13e7d80`) |
| `0x13e7df0` | `0x00000438` | `0x00000546` | 5 (`0x13e7dd4`) |

Widths stay 1920; entries 1 and 2 (1422x800, 1600x900) are other modes and are not touched.

## 1. What the UI is, and where its library sits

The layouts are `nn::ui2d` — the RTTI names survive in rodata
(`N2nn4ui2d6LayoutE` `0x103a619`, `N2nn4ui2d8DrawInfoE` `0x103a88f`, `N2nn4ui2d4PaneE`
`0x103a927`, `N2nn4ui2d8LayoutExE` `0x103a8e4`, `N2nn4ui2d6WindowE` `0x103ab4c`,
`N2nn4ui2d7TextBoxE` `0x103aa24`) and the layouts themselves are lyr archives
(`LayoutData/…/layout.lyarc/bgsh/__ArchiveShader.bnsh`, the `vs_layout`/`ps_layout`
shader packages in the profile's `shader_map.tsv`).

The image has no symbol table for them, but the `R_AARCH64_RELATIVE` relocations
(`DT_RELA` at `0x9c5080`, 153,315 entries of `{r_offset, r_info, r_addend}`) recover the
vtables: for each mangled name, the reloc whose **addend** is the name's address gives the
typeinfo's name slot, the reloc whose addend is that typeinfo gives the vtable pointer slot,
and the vtable's slots are relocations to the methods.

| class | typeinfo | vtable | methods |
|---|---|---|---|
| `ui2d::Layout` | `0x13a9c60` | `0x13a9ba0` | `0x68b6d0, 0x687e40, 0x687e60, 0x689f10, 0x68a1f0, 0x68a220, 0x68a230, 0x68a290, 0x68a2e0, 0x68a7d0, 0x68a850, 0x68a8e0, 0x68a770, 0x68a9b0, 0x688f80, 0x688400, 0x68aba0, 0x68a100, 0x68a000, 0x68ab80, 0x68ac10, 0x68a6f0, 0x6899d0, 0x6899e0` |
| `ui2d::LayoutEx` | `0x13d02c0` | `0x13d01e8` | `0x693950, 0x693a00, 0x6935d0, 0x693620, 0x693a30, 0x6937a0, 0x693680, …` |
| `ui2d::Pane` | `0x13d05a0` | `0x13d0498` | `0x69b520, 0x69c5f0, 0x69eaf0, 0x69c600, …` |
| `ui2d::Window` | `0x13d0d48` | `0x13d0c50` | `0x6ac5d0, 0x6ac5f0, 0x6afa10, …` |
| `ui2d::DrawInfo` | `0x13aa450` | `0x13aa438` | `0x690e80, 0x690c50 (empty dtor), 0x690c60` |

So the `nn::ui2d` library is the block `0x680000..0x6b4000`; the game's *layout framework*
(layout actors, "LayoutSetup/LayoutUpdate/LayoutDraw") is `0x7e0000..0x80ffff`; the game's
2D/HUD code that is not a layout is `0x900000..0x93xxxx`.

## 2. The draw chain, end to end

`0x7e4050` is a layout actor's draw:

```
0x7e4088  ldr  x21,[x20,#0x1a0]      ; the ui2d::Layout
0x7e4094  add  x24,x0,#0x108         ; arg 5: an object whose +0x50 is a VEC2  (== actor+0x158)
0x7e4098  add  x22,x0,#0x170         ; arg 7: an object whose +0x50 is a VEC2  (== actor+0x1c0)
0x7e40b4  bl   #0x7e4510             ; build the viewport
```

`0x7e4510(context, layoutActor, flags, rect, …, 1)` builds the viewport. The size it uses
is the **draw context's `+0x50` pair** (the first argument), which is the UI resolution:

```
0x7e455c  ldp  s0,s1,[x0,#0x50]      ; the draw context's size pair = the UI resolution
0x7e4560  fcvtzu w23,s1              ; viewport height  (fast path, no render-info rect)
0x7e4564  fcvtzu w28,s0              ; viewport width
...
0x7e4658  bl   #0x768ee0             ; build the projection matrix for (w28, w23)
0x7e465c  ldp  x8,x9,[x0]            ; copy 0x58 bytes of it into the DrawInfo (x21)
0x7e471c  ucvtf s0,w28 ; ucvtf s1,w23
0x7e4728  stp  s0,s1,[x20,#0x18]     ; DrawInfo viewport size, in pixels
0x7e4730  ldp  w8,w9,[x28,#0x50]     ; the same pair again, as ints (x28 = arg 0)
0x7e4734  stp  w8,w9,[x20,#8]        ; DrawInfo size field
0x7e4750..0x7e4778  bl 0x75ea90      ; draw
```

The slow path (`0x7e456c`/`0x7e45a8`, taken when the render-info flags say so) intersects
that size with a render-info rect and divides by the render scale
(`[x22+0xc0]+0x28/+0x2c`). The other caller of the same builder, `0x7e5010`, is the clearest
statement of what the number is:

```
0x7e50ac  ldp  s1,s2,[x20,#0x50]     ; the draw context's size pair
0x7e50c8  fmul s8,s0,s1              ; × a named per-layout parameter (0x69e140)
0x7e50cc  fmul s9,s0,s2
0x7e50d4  fcvtzu w4,s8               ; viewport width
0x7e50dc  fcvtzu w5,s9               ; viewport height
0x7e5108  bl   #0x768ee0             ; the projection for (w4, w5)
```

**The projection is an ortho over that size**, so the layout's coordinate space is mapped
onto the whole viewport: a viewport of 1920x1080 on a 1920x1350 canvas stretches every pane
1.25x vertically. That is the defect, and it only appeared because the canvas patch made the
canvas taller than the UI resolution — before it, canvas and UI resolution were both 1080.

## 3. Where the UI resolution comes from

The size the layouts are drawn at is the game's UI resolution, kept by one manager object
(constructor `0x8018xx`, vtable `[[0x141dae0]]+0x10`, allocated by the system object at
`[system+0xd0]` and released at `0x805674`):

| field | meaning |
|---|---|
| `+0xa40` | a 6-entry array of per-resolution `{scaleX, scaleY}` float pairs (`+0x10`, stride 8, all 1.0, built by `0x8804a0`), plus an end pointer at `+0x50` |
| `+0xa48`, `+0xa49`, `+0xa4a`, `+0xa4b`, `+0xa4c`, `+0xa4d` | mode flags (dynamic resolution on, "UI resolution follows the screen", …) |
| `+0xa50` | the selected entry index (0..5, `-1` = none) |
| `+0xa58` | **`&entry+0x18`** — the `{layoutW, layoutH}` pair of the selected entry |
| `+0x388`, `+0x3a8` | the dynamic-resolution percentages (100 = 100 %) |

The table itself, `0x13e7c30`, is 6 entries of `0x54` bytes:

| +0x00..+0x14 | +0x18 | +0x1c | +0x20 | +0x24 | +0x28 | +0x2c.. |
|---|---|---|---|---|---|---|
| 10.0f, 15.0f ×5 (per-language font sizes); entry 0's first three words are instead relocated pointers (`0x13e7bc0`, `0x13e7be0`, `0x13e7c00`) | layout W | layout H | reference W | reference H | mode enum | 10 per-element values (`LayoutPosMax*` family) |

| entry | base | W x H | reference | enum |
|---|---|---|---|---|
| 0 | `0x13e7c30` | 1920x1080 | 1280x720 | 5 |
| 1 | `0x13e7c84` | 1422x800 | 1280x720 | 2 |
| 2 | `0x13e7cd8` | 1600x900 | 1280x720 | 3 |
| 3 | `0x13e7d2c` | 1920x1080 | 1280x720 | 5 |
| 4 | `0x13e7d80` | 1920x1080 | 1280x720 | 5 |
| 5 | `0x13e7dd4` | 1920x1080 | 1280x720 | 0 |

Selection: `0x8023e0` sets the entry from bit 0 of its argument (`tst w1,#1` / `csel` 0xfc,
i.e. entry 3, or entry 0) and stores `&entry+0x18` to `[this+0xa58]`, `entry+0x54` to
`[[this+0xa40]+0x50]`; `0x802420` re-selects by the stored index `[this+0xa50]` (0..5,
clamped) and writes the index back. `0x801920` initialises `[this+0xa58]` to entry 0.

The two getters are the whole arithmetic:

```
0x802020 (width)                          0x8021c0 (height)
w8 = pct                                   w8 = pct
w8 = w8*240/100                            w8 = w8*135/100        (0x8021d4 mov w9,#0x87)
w10 = entry[+0x18]  (0x802048)             w10 = entry[+0x1c]     (0x8021fc add x10,x9,#4)
w0 = w8*w10*8 / 1920                       w0 = w8*w10*8 / 1080   (0x802200 mov w9,#0x438)
```

and the default branches use the reference pair instead (`entry+0x20` / 1280 at `0x802194`,
`entry+0x24` / 720 at `0x80233c`). In every branch the multiplier and the divisor cancel, so
**the returned UI resolution is `pct% × entry{W,H}`**: 1920x1080 at 100 % today, 1920x1350
with this patch. 2.4/1.35 = 1920/1080, which is why the two constants are not independent.

The width getter is why the UI is *not* also wrong horizontally: entry W = 1920 = the
canvas width, so the horizontal scale was already 1.0. Only the height differed.

## 4. Why these four words are the live ones

* The layout is drawn with the viewport = the UI resolution (§2), and the UI resolution is
  `pct% × entry{W,H}` (§3). The `{W,H}` pair at `entry+0x18` is the only place both the
  width (1920) and the height (1080) of the UI come from; the divisors `1920`/`1080` at
  `0x802058`/`0x802200` are the *nominal* design size and are cancelled by the entries.
* All four `{1920,1080}` entries can be selected (`0x8023e0` picks 0 or 3; `0x802420` picks
  any of 0..5 by index), and all four describe the same mode, so all four heights move. A
  UI drawn 1920 wide on device rules out entries 1 and 2 (1422x800, 1600x900), which would
  have shown a 1422- or 1600-wide HUD.
* The height field is data (`+0x1c` of each entry), never written by code: the only readers
  of the pair are the two getters, which read it and multiply. The table's only relocations
  are entry 0's three head pointers (`+0x00/+0x08/+0x10`); no `DT_RELA` entry lands on any
  `+0x18..+0x24` field, so the four rewritten words survive the load.

## 5. Expected device behaviour

* The swap chain is untouched: `[nvn] WindowInitialize swap chain 3 textures, interval 1,
  first 1920x1350` still prints, and the world still fills the whole panel
  (`010028600EBDA000-canvas.md` §4).
* The UI is drawn at 1:1 canvas pixels: the A/B button discs come back as 40x40, text and
  icons at their authored size, no 1.25x vertical stretch, no 0.8x horizontal squeeze.
* Because the UI resolution now equals the canvas, the layouts are anchored against the real
  screen: root-anchored panes span all 1350 rows (top-anchored stay at the top,
  bottom-anchored sit on the canvas bottom, centre-anchored stay at the canvas centre) and
  the title-card art no longer has to fill a 16:9 box stretched to 1350.
* The present is already uniform (2853/1920 = 1.4859, 2007/1350 = 1.4867), so nothing in
  the present changes: `DM_PRESENT_FILL=stretch` stays a no-op.
* If a full-screen 16:9 layout (a menu background) is authored with absolute 1080-row
  coordinates and is *not* root-anchored, it will now occupy the top 1080 rows at 1:1
  instead of being stretched over 1350 — the picture is still correct, the layout simply
  does not use the extra 270 rows. That is the intended trade: native size first.

## 6. Rejected alternates (and why)

* **`0x8a86a0` `mov w0,#0x438` → `#0x546`** — the game's `GetScreenHeight()` (paired with
  `GetScreenWidth()` `0x8a8690` = 1920, and `0x8a86b0/0x8a86c0/0x8a86d0/0x8a86e0` = the
  1280x720 pair). It is live and used by ~60 sites in the 2D/HUD code, which convert UI
  positions to NDC by *half* of it (`0x99d924`, `0x99e24c`, `0x90bd6c`, `0x921610`,
  `0x908404`, `0x908474`, `0x90bc18`, `0x16e1a8`, `0x16e1b8`). That is the same 1.25 factor
  for those draws, but it is *not* the layout path: nothing in the layout framework
  (`0x7e0000..0x80ffff`) or in `nn::ui2d` calls either getter (`--callers` on both), and the
  layout's viewport is the UI resolution instead. Patching it would move those 2D objects
  (and the off-screen indicators) without touching the HUD. Left alone.
* **`0x802200` `mov w9,#0x438` → `#0x546`** (the height getter's divisor) — same "1080 in UI
  code", but it is a *divisor*: raising it to 1350 would return `pct*1.35*1080/1350` = a
  **864**-tall UI resolution, shrinking the UI by 0.8. Rejected.
* **`entry+0x24` (720) and `entry+0x20` (1280)** — the reference pair used by the default
  getter branch; it cancels against its own divisor, so changing it changes nothing.
* **`0xda74a8` (1080.0f)** — the only 1080.0f in rodata that is read, by the screen-rect
  builders `0x8a9040` (`{0,0,1920,1080}` docked / `{0,0,1280,720}` handheld) and `0x8a9120`,
  whose only callers are the off-screen indicator code at `0x171adc`/`0x171afc` and
  `0x171b0c`-style clamps. Not the layout; rejected.
* **The 16:9 constant `0xda6934`** — already registered in `duo/research/games.tsv` and rewritten to
  the drawable ratio by `install_const`; it is the camera's aspect, not the UI's.
* **`0x8a8730`/`0x8a8750`** (factories returning `{1920.0f,1080.0f}` and `{1280.0f,720.0f}`)
  — `0x8a8730` has no `bl` caller at all; `0x8a8750` has two (`0x3f154c`, `0x3f82c0`), both
  unrelated to the layout. Dead for this purpose.
* **The per-resolution scale array at `[manager+0xa40]+0x10`** (6 float pairs, all 1.0, set
  by `0x8804a0`, written by `0x802a70`/`0x802ae0`/`0x802b04` on resolution changes) — a
  *layout* scale, not the projection size; with the UI resolution matching the canvas it
  should stay 1.0. If a device test ever shows the UI scaled by 1.25 with the correct
  viewport, this array is the next thing to look at.
* **`0x40b81c` / `0x40b890`** (the canvas) — already patched; changing them again would undo
  the world fix.

## 7. Residual risk and where to look next

The one assumption this patch rests on is that the draw context's `+0x50` size pair is the
UI resolution (the `entry{W,H}` pair). §2 proves the projection is built from
`[context+0x50]`; §3 proves the UI resolution is `pct% × entry{W,H}` and that the manager at
`[system+0xd0]` (reached from `0x29c974` and released at `0x805674`) is its only owner. What
is *not* proven statically is the writer of `[context+0x50]`. If a device test shows the HUD
still stretched, the next levers, in order:

1. **`[context+0x50]`** — find its writer (the layout actor/context setup, `0x7e0000..0x7e4000`
   for the actors, or the UI system that creates them). If it is fed the *display* size
   (`[display+0x120/+0x124]`, i.e. 1920x1350) instead of the UI resolution, this patch cannot
   win on its own: the pair then has to be fed the UI resolution (or 1080x1350 with a
   centring offset of 135).
2. **The per-layout parameter** read by name at `0x7e5098`/`0x7e50a0` (`0x69e140`, name
   string at `0xd6b2c5`) and multiplied into the pair at `0x7e50c8`/`0x7e50cc`. If a device
   test shows the UI scaled by 1.25 with the correct viewport, this multiplier is the
   remaining factor and its value in the layout parameter block is the lever.

Also worth checking on the first run: the UI resolution manager's percentages
(`+0x388`/`+0x3a8`, both 100) and the flags `+0xa48`/`+0xa49`, which decide which getter
branch (entry pair or reference pair) runs — both branches give `pct% × entry{W,H}` today,
so either is fine, but a non-100 percentage means the game is scaling the UI itself.

## 8. Reproducing the evidence

```sh
python3 dm/tools/nso.py <ExeFS>/main /tmp/sm3dw.bin
python3 dm/tools/sdis.py /tmp/sm3dw.bin 0x8021c0 45     # the height getter: *entry[+0x1c], /1080
python3 dm/tools/sdis.py /tmp/sm3dw.bin 0x802020 20     # the width getter:  *entry[+0x18], /1920
python3 dm/tools/sdis.py /tmp/sm3dw.bin 0x8023e0 16     # entry selection -> [this+0xa58]
python3 dm/tools/sdis.py /tmp/sm3dw.bin 0x7e4050 30     # layout draw -> 0x7e4510
python3 dm/tools/sdis.py /tmp/sm3dw.bin 0x7e455c 60     # viewport = [context+0x50]
python3 dm/tools/sdis.py /tmp/sm3dw.bin 0x7e5010 80     # the same pair × a named parameter -> 0x768ee0
python3 -c "import struct;d=open('/tmp/sm3dw.bin','rb').read();\
[print(hex(0x13e7c30+e*0x54), struct.unpack_from('<6I',d,0x13e7c30+e*0x54+0x18)) for e in range(6)]"
```

The reloc-derived vtables (§1) come from `DT_RELA` at `0x9c5080` (`0x382548` bytes, 24-byte
entries); the typeinfo of a class is the reloc target minus 8, and a vtable is the run of
relocations whose addend is that typeinfo.
