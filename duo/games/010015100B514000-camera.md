# Super Mario Bros. Wonder - the in-game camera projection aspect

Build `cd6e42aee7934f4d8393cd43893ae25e` (v0); `main` at
`/path/to/work/010015100B514000_build/extract/v0/ExeFS/main`.
All offsets are **image offsets**, the space `patch_nso.py` and `duo/research/games.tsv` number:
text `0x0..0x2012880` (32 MiB), ro `0x2013000` (size `0x11f5328`), data `0x3209000`,
bss `0xa83d8`.

Image identity checked before anything else: `nso.load(main).image` is byte-identical to
`/tmp/wonder.bin` for `0x3645000` bytes (sha256 prefix `9cd3a7438638fd036f2cf8e8e54c8e75`),
build id `cd6e42aee7934f4d8393cd43893ae25e`. Every address below was read from that image.

---

## 0. The answer in one paragraph

The camera's perspective projection is a sead-shaped `Projection` block - fovy `+0x98`,
sin `+0xa4`, cos `+0xa8`, tangent `+0xac`, **aspect `+0xb0`**, near/far `+0xb4`/`+0xb8`.
It is refreshed from a camera-parameter block `Q = [camera_manager+0x1f0]`, and the
**authored aspect field is `Q+0x15c`**, staged into `Q+0x218` and then applied to the
projection by the single pair

```
0x10f47c  ldr s0, [x8, #0x218]     ; aspect, from the camera params
0x10f480  strb w23, [x22, #8]      ; projection dirty flag
0x10f484  str s0, [x22, #0xb0]     ; projection aspect
```

`0x10f47c` is the registered site (an eligible `ldr s<d>,[x<n>,#imm]`, word `0xbd421900`).
Replacing it with the constant stub gives `s0 = 1.4215247` every time this projection
refresh runs, which is exactly the 3D World trick applied one level up: there the site fed
`+0x124/+0x128` of a camera object, here it feeds `+0xb0` of the projection itself.

## 1. Why the 3D World shapes are absent in this build

| probe | result |
|---|---|
| float 16:9 `0x3FE38E39` in text/ro/data | **0 hits** |
| double 16:9 `0x3FFC71C71C71C71C` | **0 hits** |
| rodata floats for the viewers | only `1.7777780294` at ro `0x29b5fe8` (see 4.6) |
| `1920.0f` / `1080.0f` | no aligned occurrence; every 4-byte hit (`0x2054ade`, `0x251df7f`, ...) is misaligned, i.e. coincidence inside strings/blobs |
| `duo/tools/find_aspect.py <main>` | 4 672 `fdiv`, **0** scored candidates, `16:9 constants at []` |
| `fdiv` whose two operands are loaded from the same base at adjacent offsets | **0** |

The `fdiv`/constant levers are therefore empty here: the aspect is **authored data on the
camera rig**, not a constant and not a division. The only native lever is the instruction
that copies it into the projection - which is what the site list exists for.

## 2. The chain, link by link

### 2.1 The camera manager dispatches a projection refresh (`0x10f340`)

This block is inside the large camera/state routine whose only `ret` is at `0x10f5dc`
(`0x105xxx..0x10f5dc`; a `ret` scan of `0x10c000..0x10f800` finds no other).

```
0x10f340  ldr  x0, [x21, #0x80]      ; x21 = camera manager
0x10f344  bl   #0x6b3560            ; -> the current projection object (x22)
0x10f348  cbz  x0, #0x10f498        ; no projection -> skip
0x10f34c  ldr  x23, [x21, #0x1f0]   ; x23 = Q, the camera parameter block
0x10f350  mov  x22, x0              ; x22 = projection
0x10f354  mov  x1, x22
0x10f358  add  x0, x23, #0x168
0x10f35c  bl   #0x1cec29c           ; copy projection -> Q+0x168 (shadow)
0x10f360  add  x0, x23, #0x200
0x10f364  add  x1, x22, #0x98
0x10f368  mov  w2, #0x24            ; 0x24 = 36 bytes = the 9-float projection block
0x10f36c  bl   #0x200f320           ; memcpy(Q+0x200, projection+0x98, 0x24)
```

The `memcpy` of exactly `0x24` bytes from `projection+0x98` is the decisive layout proof:
the nine floats at `+0x98 .. +0xb8` are the projection's scalar set, and `+0xb0` sits inside
it at index 6 - the sead aspect slot (3D World: fovy `+0x98`, tan `+0xac`, aspect `+0xb0`).

### 2.2 The camera params are staged into `Q+0x200..0x223`

```
0x10f370  ldr  x8, [x21, #0x1f0]
0x10f37c  ldr  s0, [x8, #0x148]
0x10f384  str  s0, [x8, #0x200]     ; fovy   <- Q+0x148
0x10f38c  ldr  s0, [x8, #0x14c]
0x10f394  str  s0, [x8, #0x204]     ;        <- Q+0x14c
0x10f3a0  ldr  s1, [0x29b5cb4]      ; 0.017453292 = deg -> rad
0x10f3a4  ldr  s0, [x26, #0x150]
0x10f3a8  fmul s0, s0, s1
0x10f3b0  str  s0, [x26, #0x208]    ; fov(deg)*pi/180 <- Q+0x150
0x10f3ac  fmul s8, s0, s9           ; s9 = 0.5f
0x10f3b8  bl   #0x200e8f0 ; 0x10f3bc  str s0,[x26,#0x20c]   ; sin(half fov)
0x10f3c4  bl   #0x200e910 ; 0x10f3c8  str s0,[x26,#0x210]   ; cos(half fov)
0x10f3d0  bl   #0x200e9b0 ; 0x10f3d4  str s0,[x26,#0x214]   ; tan(half fov)
0x10f3e8  ldr  x10, [x9]            ; x9 = Q+0x154
0x10f3ec  str  x10, [x9, #0xc8]     ; near/far (8 bytes) -> Q+0x21c
0x10f3f4  ldr  s0, [x8, #0x15c]     ; <-- THE AUTHORED ASPECT, Q+0x15c
0x10f3fc  str  s0, [x8, #0x218]     ; aspect -> Q+0x218
```

`Q+0x154..0x158` is read as one 8-byte quantity and lands in `Q+0x21c..0x220`, i.e. the
near/far pair - independent confirmation that `0x148..0x15c` are **scalars**
(fovy, fovy2, fov-deg, near, far, aspect), not a transform: a matrix element would not be
usable as near/far.

### 2.3 The staged block is applied to the projection (guarded)

```
0x10f400  ldrb w8, [x21, #0x8c]
0x10f404  tbz  w8, #2, #0x10f488     ; only when camera-manager flag bit 2 is set
0x10f408  ldr  x26, [sp, #0xe8]      ; camera object; [x26] = Q
0x10f410  ldr  s0, [x8, #0x200] ; 0x10f418  str s0,[x22,#0x98]   ; fovy
0x10f420  ldr  s0, [x8, #0x204] ; 0x10f428  str s0,[x22,#0x9c]
0x10f430  ldr  s0, [x8, #0x208] ; 0x10f438  str s0,[x22,#0xa0]
0x10f440  bl   #0x200e8f0       ; 0x10f444  str s0,[x22,#0xa4]   ; sin
0x10f44c  bl   #0x200e910       ; 0x10f450  str s0,[x22,#0xa8]   ; cos
0x10f458  bl   #0x200e9b0       ; 0x10f45c  str s0,[x22,#0xac]   ; tan
0x10f46c  ldr  x8, [x8]         ; 0x10f474  stur x8,[x22,#0xb4]   ; near/far
0x10f47c  ldr  s0, [x8, #0x218] ; <-- SITE
0x10f480  strb w23, [x22, #8]        ; dirty
0x10f484  str  s0, [x22, #0xb0] ; <-- aspect stored
0x10f488  ldr  x8, [sp, #0xe8]
0x10f48c  ldr  x8, [x8]          ; Q
0x10f490  add  x9, x8, #0x168
0x10f494  b    #0x10ed1c
```

When the flag is clear the block is skipped and the projection keeps its previous values;
when it is set, the whole scalar set - fovy, sin, cos, tan, near/far and **aspect** - is
rewritten from `Q`. That is a projection param apply, not a copy of an unrelated struct.

## 3. Why the chosen word is the live one

1. **Uniqueness.** A scan of the whole text segment for `ldr s<d>,[x<n>,#0x218]` followed
   within five instructions by `str s<same d>,[x<m>,#0xb0]` returns **exactly one pair** in
   the entire module: `0x10f47c -> 0x10f484`. Nothing else feeds `+0xb0` from the camera
   parameter block.
2. **The layout is the sead one.** `memcpy(Q+0x200, projection+0x98, 0x24)` at `0x10f36c`
   treats `+0x98..+0xb8` as one nine-float record; `+0xb0` is inside it; the sin/cos/tan
   triplet computed from half the fov is written at `+0xa4/+0xa8/+0xac`, exactly where 3D
   World keeps `tangent`. Independent readers - `0x171d0 ldr s0,[x20,#0xb0]; str s0,[x19,#0x174]`
   and `0xb3530 ldr s3,[x9,#0xb0]; str s3,[x0,#0x2ac]` - copy the same six-float run
   (`+0xa4,+0xa8,+0xac,+0xb0,+0xb4,+0xb8`) wholesale, so `0xb0` is a per-object scalar of
   that record in every user, not a coincidence of one function.
3. **The site's consumer is only the aspect store.** Between the load and the store there
   is nothing but `strb w23,[x22,#8]` (the dirty flag). Dropping the load has no side
   effect, which is what `const_stub` requires.
4. **The site is an accepted form.** `duo_aspect.form_ok(0xbd421900)` is `True`;
   capstone decodes it as `ldr s0, [x8, #0x218]`. With `DM_DUO_ASPECT=2853:2007` the stub is
   `[0x1c000040, 0x1783fd1f, 0x3fb5e1b1]` at stub address `0x2010000`, which decodes to
   `ldr s0, #0x2010008` ; `b #0x10f480` ; `.float 1.4215247` (bits `0x3FB5E1B1`), and the
   site word becomes `b <stub>` (`branch(0x2010000, 0x10f47c)` in range). Checked by calling
   `duo_aspect.const_stub`/`branch`/`form_ok` directly on this image; nothing was written.
5. **Nothing else in the image stores an aspect into this record.** Of the 91
   `str s,[x,#0xb0]` sites only two write the projection record's `+0xb0`: `0x10f484`
   (this one) and `0x10ee44` (the zoom path, 4.3).

## 4. Rejected alternates, with addresses

### 4.1 `0x10f3f4  ldr s0,[x8,#0x15c]` - the aspect's source field (fallback)
Eligible form (`0xbd415d00`), and patching it would put the ratio into `Q+0x218` so that
*every* consumer of the staged field sees it. Rejected as the primary because it changes a
shared camera parameter that 28 `ldr s,[x,#0x218]` sites read (other objects with the same
offset are possible, and the staged field also feeds `Q+0x168` shadow copies). It is the
first thing to try if `0x10f47c` turns out to sit on a path the in-game camera never takes.

### 4.2 `0x10f484  str s0,[x22,#0xb0]`
The store itself. Not an eligible form, and there is no constant to place in it.

### 4.3 `0x10ee44  str s0,[x24,#0xb0]` - the only other writer of a projection aspect
```
0x10eaec  fdiv s8, s8, s9          ; a scale (zoom/timescale)
0x10eb10  ldr  x8, [sp, #0xe8]
0x10eb14  cbnz x8, #0x10ee28
...
0x10ee28  ldr  x24, [sp, #0xe8]
0x10ee30  ldr  x8, [x24]           ; vtable
0x10ee34  ldr  x8, [x8, #0x38]     ; virtual getter
0x10ee3c  fmul s0, s8, s0
0x10ee44  str  s0, [x24, #0xb0]    ; aspect * scale
```
Reached only from `0x10eb14`/`0x10eb68`, i.e. the same zoom block that multiplies the
tangents at `0x10eb20`/`0x10eb24` (`fmul s1,s8,s1` / `fmul s0,s8,s0`) and divides them at
`0x10eb84`/`0x10eb88`. It is a fov-zoom applied on top of the projection, not the param
apply, and `str` is not an eligible form anyway. A zoom that runs after the patch will
scale the injected ratio, which is the intended behaviour of that effect.

### 4.4 `0x11a488  str s25,[x0,#0x218]`
A min/max clamp writer of the same `0x204..0x218` cluster in a different class
(`fcmp`/`b.pl`/`fmov` around it). Not the camera param block owner.

### 4.5 `0x116c78`, `0x117358`, `0x131a30`, `0x287a78`, `0x289258` - other `str s,[x,#0x15c]`
These are 3x3 basis/transform writers: `0x117358` fills `0x140..0x160` as one contiguous
run and `0x131a30` does the same for `0x144..0x16c`; `0x289244` clamps the field with
`fminnm ...,#1.0`. `Q`'s `+0x15c` cannot be a matrix element because `+0x154/+0x158` are
consumed as the near/far pair (2.2). Same offset, different class - not this field.

### 4.6 `ro 0x29b5fe8 = 1.7777780294`
The only 16:9-ish float in the image. Neighbours are `0.26, 0.38, -0.785398 (-pi/4),
-99999.0, 78.233, 1.553343 (pi/2), 4.31969` - a bag of unrelated constants. No
`adrp`+`ldr`/`ldur`/`add` reference to this address exists (checked both `0x29b5000` and
`0x29b6000` pages), so it is not the camera's aspect. Also not usable as the `const`
column, which requires the exact `0x3FE38E39` word and would refuse this value anyway.

### 4.7 `0xa7858  str s1,[x19,#0xb0]`
A six-float projection-record copy (`0xa7840..0xa7868`: `+0x9c,+0xa0,+0xac,+0xb0,+0xbc,+0xc0`).
It propagates whatever aspect the record already has; patching it would change nothing
about where the 16:9 comes from.

### 4.8 `0x10eb20`/`0x10eb24`, `0x10f330`/`0x10f334`
`fmul` of the tangents by the zoom scale - fov, not aspect.

### 4.9 `0x5a49d0  mov w8,#0x438` (canvas height)
Already a row in `duo/research/res.tsv` and documented in `duo/games/010015100B514000-canvas.md`.
That is the swap-chain canvas, not the camera; this report does not touch it.

## 5. Status and the device test

Static only. **No `nx build --prepare-xcode` was run**: the aspect block only emits when the
build id has a row in `duo/research/games.tsv`, and adding that row is outside this ticket (the file
is off limits here), so a build would prove nothing about this site. The row is proposed at
the end.

The two things a device run must answer, in order:

1. Patch, build with `DM_DUO=1`, present with **Stretch**, load a level. If the world widens
   and characters are the right shape, `0x10f47c` is live.
2. If nothing changes, the `0x10f400` flag gate was not taken on that path - switch the row
   to `0x10f3f4` (4.1), which stages the ratio into `Q+0x218` before the gate.

Score it the way `duo/design/aspect.md` §5 does (normalized cross-correlation of static
scenery against the cropped 1080 frame), not by eye.

Known residual unknowns, stated plainly: the writer of `Q+0x15c` itself was not found among
the `str s` forms (the five `+0x15c` stores are transform classes, 4.5); it is either
authored rig data loaded from a resource, or written by a form this scan does not model
(128-bit `str q`/`st1`). Either way it does not change the lever: the projection's aspect is
set at `0x10f484` from `0x10f47c`, and the `+0x218 -> +0xb0` pair is unique in the module.

## 6. Reproducing the evidence

```sh
python3 dm/tools/nso.py <ExeFS>/main /tmp/wonder.bin      # image, build id cd6e42ae...
python3 duo/tools/find_aspect.py <ExeFS>/main --window 4  # 4672 fdiv, 0 scored, no 16:9 const
```

With `dm/tools` on `sys.path` and capstone's `md.skipdata = True` (mandatory - without it
the disassembly stops at the first data word in `.text` and every xref scan silently
returns nothing), the scans behind section 3 are: the `0x3FE38E39`/16:9-double/`1920.0f`
byte probes over all three segments; the `str s`/`ldr s` offset tally (91 `+0xb0` stores,
192 `+0xb0` loads); the `ldr s,[x,#0x218]` -> `str s,[x,#0xb0]` pair scan (one hit); the
`str s,[x,#0x218]`/`str s,[x,#0x15c]` writer lists; and `duo_aspect.form_ok` /
`const_stub` / `branch` run directly on the image.
