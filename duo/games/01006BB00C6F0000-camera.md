## 0. The answer in one paragraph

This is not sead: the image has no `sead::`, `agl::` or `PerspectiveProjection` string, and the sead slots
(`+0xac` tangent, `+0xb0` aspect) hold nothing camera-like here (section 5.5). Grezzo's own render camera (called
**R** below) keeps its projection inputs as scalars: **aspect `R+0x1dc`**, fovy `R+0x1e0` (radians), near `R+0x1d4`,
far `R+0x1d8`, ortho flag `R+0x1e4`, view matrix `R+0x20..+0x5f`. Its projection is built by the vtable method
`0x1025d00` (vtable slots at ro `0x1436820`, `0x1642110`), which divides by `R+0x1dc`. Every camera update
(`0x10540`, a function pointer at ro `0x1435c38`) rewrites `R+0x1dc` - from the rodata 16:9 constant `0x16afba4`
unless the active camera's parameter block overrides the aspect - and the same update builds a **second**
view/projection block that divides by the constant directly. When no camera is active, the reset `0xc0a40` writes
`R+0x1dc` from a `movz`/`movk` 16:9 pair. The four instructions that produce those aspect values are the sites:

| offset | word | instruction | produces |
|---|---|---|---|
| `0x1092c` | `bd4ba520` | `ldr s0, [x9, #0xba4]` (ro `0x16afba4` = 1.7777778) | `R+0x1dc`, the normal path |
| `0x114a0` | `bd4572e0` | `ldr s0, [x23, #0x570]` | `R+0x1dc` when the camera parameter block overrides the aspect |
| `0x10b58` | `bd4ba542` | `ldr s2, [x10, #0xba4]` (same constant) | the divisor of the second projection's `m[0]` |
| `0xc0c24` | `5291c729` `72a7fc69` | `mov w9, #0x8e39` ; `movk w9, #0x3fe3, lsl #16` | `R+0x1dc` in the no-camera reset |

Column 3 stays `-`: the constant `0x16afba4` is also read at `0x1023d40` to compute a render width
(`(1080 - 36*i) * 16/9`), so replacing it would pull the canvas lever that `duo/design/aspect.md` rejects.

## 2. The chain

### 2.1 The camera update `0x10540` picks the active camera and its render camera

```
0x10564  adrp x21, #0x1cac000
0x1056c  ldr  x19, [x21, #0xb30]     ; camera manager
0x10574  ldp  x23, x20, [x19]        ; C = active camera (shared pointer)
0x105a0  cbz  x23, #0x10e50          ; no camera        -> reset 0xc0a40 (2.5)
0x105a8  tbnz w8, #0x1e, #0x10e50     ; C+0x40 bit 30     -> reset
0x105d4  cmp  w21, #0x17 ; b.ne #0x10e6c   ; kind mismatch -> reset
0x105dc  ldr  x24, [x23, #0x2a8]     ; R = C's render camera
0x10900  stp  q21, q7, [x24, #0x20]  ; R view matrix
0x10904  stp  q20, q0, [x24, #0x40]
```

When `C+0x700` bit 0 (dirty) is clear the view comes from the cache (`0x10e74..0x10e84`, then `b 0x10900`), so the
projection-parameter block below runs on every update either way.

### 2.2 The projection parameters are copied into R (the aspect site)

```
0x10908  ldr  x8, [x23, #0x2a8]      ; R
0x1090c  ldrb w9, [x23, #0x524]      ; C parameter flags
0x10910  tbz  w9, #1, #0x10ef0       ;   bit 1 clear -> fovy default 0.3490659 (ro 0x16afcac)
0x10914  ldr  s0, [x23, #0x564]
0x10918  str  s0, [x8, #0x1e0]       ; R fovy
0x1091c  ldr  x8, [x23, #0x2a8]
0x10920  ldrb w9, [x23, #0x524]
0x10924  tbnz w9, #4, #0x114a0       ;   bit 4 set -> override (below)
0x10928  adrp x9, #0x16af000
0x1092c  ldr  s0, [x9, #0xba4]       ; <-- SITE: 16:9 = 1.7777778
0x10930  str  s0, [x8, #0x1dc]       ; R aspect
0x10934  ldr  x8, [x23, #0x2a8]
0x10938  ldr  w9, [x23, #0x524]
0x1093c  tbz  w9, #2, #0x10ed8       ;   near default 0.1 (ro 0x16af9b4)
0x10940  ldr  s0, [x23, #0x568]
0x10944  tbz  w9, #3, #0x10ee4       ;   far default 4096.0 (ro 0x16af790)
0x10948  ldr  s1, [x23, #0x56c]
0x1094c  str  s0, [x8, #0x1d4]       ; R near
0x10950  str  s1, [x8, #0x1d8]       ; R far
...
0x114a0  ldr  s0, [x23, #0x570]      ; <-- SITE: the overriding aspect
0x114a4  b    #0x10930
```

The parameter block is five scalars with one flag bit each - bit 0 `+0x560` (default 10.0), bit 1 fovy `+0x564`,
bit 2 near `+0x568`, bit 3 far `+0x56c`, bit 4 **aspect `+0x570`** - and the unflagged value is the built-in
default. The same five-slot layout, shifted by `0x510` (flags `+0x14`, values `+0x50..+0x60`), is what the camera
controller apply `0xc1a80` writes (`0xc1b84`, `0xc1bcc`, `0xc1c14`, `0xc1c5c`, `0xc1ca8 str s0,[x0,#0x60]` with
flag `orr ... #0x10`) and what the interpolator `0xc31a0` blends, with the same defaults
(10.0, 0.3490659, 0.1, 4096.0, 16:9) in its jump table (`0xc3298`, `0xc31fc`, `0xc3248`, `0xc3270`, `0xc3224`).

### 2.3 R's projection builder divides by `R+0x1dc`

`0x1025d00(R, index, ...)` (vtable method; no direct `bl`): `ldrb w8,[x19,#0x1e4]` selects ortho (`0x1025d60`) or
perspective (`0x1026658`). The perspective path:

```
0x102665c  ldr  s0, [x19, #0x1e0]    ; fovy
0x1026664  fmul s4, s0, s3           ; fovy/2
0x102666c  ldr  s1, [x19, #0x1dc]    ; aspect
0x1026670  ldr  s2, [x19, #0x1d4]    ; near
0x1026694  ldr  s3, [x19, #0x1d8]    ; far
...                                   ; inline sin/cos of fovy/2 (polynomials from 0x1c93e58/0x1c93e60)
0x10268b0  fdiv s23, s4, s1          ; m[0] = cot / aspect   (a matrix element: NOT a site)
0x10268e0  stp  q5, q19, [x19, #0x60] ; R matrices +0x60..
```

Other readers of the field - `0x487efc`, `0x94b498`, `0x94e864`, `0xb19a98`, `0x1025f1c` (ortho) - each load
`+0x1e0` and halve it next to the `+0x1dc` load (frustum users). They read the field, so they follow it.

### 2.4 The second projection uses the constant directly

Right after 2.2 the same function builds another view/projection block from the scene's render camera
`x20 = [x25+0x560]` (an R: it reads `+0x1e0`, `+0x1d4`, `+0x1d8`, and its view is copied from `+0x20..+0x5f` at
`0x10bc4`/`0x10bcc`), but it never reads `+0x1dc`:

```
0x109ec  ldr  s0, [x20, #0x1e0]      ; fovy
0x109fc  fmul s2, s0, s1             ; fovy/2
0x10a04  ldr  s8, [x8, #0x1d4]       ; near
0x10a24  ldr  s0, [x8, #0x1d8]       ; far
0x10a68  ldr  x19, [x20, #0xb30]     ; x20 = page 0x1cc8000: global block owner
0x10a84..0x10b04                      ; inline sin/cos -> s1 = tan(fovy/2)
0x10b18  ldr  x8, [x19, #0x50]       ; destination block
0x10b1c  fdiv s3, s17, s1            ; cot = 1/tan
0x10b58  ldr  s2, [x10, #0xba4]      ; <-- SITE: 16:9 = 1.7777778
0x10b68  fdiv s4, s3, s2             ; m[0] = cot / aspect   (a matrix element: NOT a site)
0x10b78  mov  v3.s[0], v4.s[0]
0x10bd8  stp  q3, q2, [x8, #0x10]    ; projection columns
0x10bdc  stp  q1, q0, [x8, #0x30]
0x10bd0  stp  q4, q5, [x8, #0x50]    ; + the camera's view matrix
```

Leaving this at 16:9 while R uses the Duo ratio would give whatever draws with `[[0x1cc8b30]+0x50]` a different
horizontal scale than the scene. Its consumer was not traced ([INFERENCE] an effects-style subsystem that takes the
scene's view and projection).

### 2.5 The no-camera reset writes R's aspect with a movz/movk pair

`0xc0a40` is called only from `0x10e6c` (2.1's reset branch), and then execution continues at `0x10954`, i.e. into
2.4:

```
0xc0a4c  adrp x20, #0x1c97000
0xc0a50  ldr  x19, [x20, #0x188]
0xc0a58  ldr  x8, [x19, #0x560]      ; R of the scene
...                                   ; default view written to R+0x20..+0x5f (0xc0bdc..0xc0c08)
0xc0c24  mov  w9, #0x8e39            ; <-- SITE (pair)
0xc0c28  movk w9, #0x3fe3, lsl #16   ;     w9 = 0x3fe38e39 = 16:9
0xc0c2c  str  w9, [x8, #0x1dc]       ; R aspect
0xc0c40  str  s0, [x8, #0x1e0]       ; fovy
0xc0c48  str  x9, [x8]               ; x8 = R+0x1d4: near 1.0, far 1000.0 (0x447a00003f800000)
```

## 3. Why each registered word is the aspect itself, not a matrix element

* `0x1092c` loads the 16:9 float and its only consumer is the next instruction, `str s0,[x8,#0x1dc]`. `+0x1dc` is a
  scalar written next to fovy/near/far, and the builder divides the cotangent by it afterwards (`0x10268b0`). With
  the stub, `s0 = 1.4215247`, the builder divides once, by the new ratio.
* `0x114a0` loads the parameter-block aspect and goes straight to the same store (`b 0x10930`).
* `0x10b58` loads the divisor; the matrix element is produced by the following `fdiv s4, s3, s2` at `0x10b68`, which
  is left alone. Patching `0x10b68` instead would be the Galaxy 2 mistake (`cot/aspect` replaced by the ratio).
* `0xc0c24..0xc0c28` builds the bits `0x3fe38e39` that `0xc0c2c` stores into `+0x1dc`; the pair stub loads the
  ratio's bits into `w9` and resumes at `0xc0c2c`.

No registered instruction computes anything from the aspect; each one is the producer of the value the projection
later divides by, so the ratio is applied exactly once.

Writers of `R+0x1dc`, so that nothing else feeds it: float stores `0x10930` (2.2) and `0xfd7b4c` (the
field-by-field copy `0xfd7a50`, called from `0xfd794c`, which only propagates); 32-bit stores `0xc0c2c` (2.5) and
`0x19144` (the constructor, 5.2). Wide stores that cover `+0x1dc` in the camera code ranges are other objects:
`0x10261dc` writes `[R+0x270]+0x1d8`, `0xdbc4`/`0xfdb368` zero-fill other structures, `0x1c014`/`0xfd9ac0` store
pointer pairs. The other `str s,[x,#0x1dc]` hits (`0x1164e98`, `0x116ddfc`, `0x117741c..0x1179dc8`, `0x12c32d4`,
`0x12f3fe0`/`0x1395d34` on `sp`) are colour channels, bounds and stack temporaries.

## 4. Dry run of the repo's rewriter (nothing written)

`duo_aspect.install_sites_const` called in memory on the decompressed image with `sites_for` stubbed to this row and
the patch area at this build's `PATCH_OFF` (`0x1ce0000`, from `patched_v131072/main.fixups.tsv`):
`ratio_bits()` = `0x3fb5f485` (1.4215247), 4 sites, every branch in range.

```
0x1092c  bd4ba520 -> 14733db5  b #0x1ce0000   stub 1c000040 178cc24b 3fb5f485 : ldr s0, #0x1ce0008 ; b #0x10930
0x114a0  bd4572e0 -> 14733adb  b #0x1ce000c   stub 1c000040 178cc525 3fb5f485 : ldr s0, #0x1ce0014 ; b #0x114a4
0x10b58  bd4ba542 -> 14733d30  b #0x1ce0018   stub 1c000042 178cc2d0 3fb5f485 : ldr s2, #0x1ce0020 ; b #0x10b5c
```

## 5. Rejected candidates

### 5.1 The rodata constant `0x16afba4` as column 3
Its seven readers: `0x1092c` and `0x10b58` (the sites); `0xc1c84` (dead: with flag bit 4 clear the constant is
loaded and `tbz w8,#4,#0xc1cb0` skips the store); `0xc3228`/`0xc3edc` (interpolation defaults of the parameter
block - whatever they produce reaches R only through `0x114a0`, a site); `0x85f824` (stores into `[x24+0x460]` of a
controller in `0x85f620`, callers `0x836fb8`/`0x8454e4`/`0x85d6d8`; no `ldr s,[x,#0x460]` in `0x850000..0x870000`,
and not a writer of `R+0x1dc`); and **`0x1023d40`**:

```
0x1023d30  mul   w8, w22, w8          ; w8 = -0x24
0x1023d34  add   w8, w8, #0x438       ; height = 1080 - 36*i
0x1023d3c  scvtf s0, w8
0x1023d40  ldr   s1, [x10, #0xba4]    ; 16:9
0x1023d44  fmul  s0, s0, s1
0x1023d48  fcvtzs w10, s0             ; width
0x1023d6c  str   w10, [x21, x12]      ; width/height pairs at +0x6e38/+0x6e3c and +0x6e40/+0x6e44
```

A render-size table: patching the constant would make the widths `1080*1.42 = 1535`, the canvas lever.

### 5.2 The constructor pair `0x1913c`
`0x190a0` (called from `0x18068`, `0x18d94`, `0x18ea0`) is R's constructor default (`0x19144 str w8,[x0,#0x1dc]`).
The scene's R is rewritten by 2.2 or 2.5 on every update, and patching the constructor would also change every other
instance of the class.

### 5.3 The other 16:9 pairs
`0xb5d1c`, `0xb9d18`, `0xc4f88`, `0xc6c8c`, `0x7dc740` initialise five-float default blocks
{10.0, 0.3490659, 0.1, 4096.0, 16:9} with a `0xf` word stored right after (`0xb9d28`, `0xc4f9c`, `0x7dc754`);
`0x111fb4`, `0x112f08`, `0x7ddd14` build the same kind of block on the stack; `0xc7e60` and `0x7f6318`/`0x7f75d4`
store into other structures. [INFERENCE] `0xf` is the override mask with the aspect bit clear. Whatever these
blocks carry reaches the projection only through `C+0x570` -> `0x114a0`, which is a site.

### 5.4 Matrix elements
`0x10268b0 fdiv s23,s4,s1` and `0x10b68 fdiv s4,s3,s2` are `cot/aspect`. Registering either would apply the ratio
twice (the Galaxy 2 squash).

### 5.5 find_aspect's sead-shaped hits
* `0x11e3a58`/`0x11e3a5c` and `0x11f0c90`: `+0xb0` of an object served by the setter family
  `0x11f0c20..0x11f0ce0` (`+0xa4/+0xa8/+0xac/+0xb0`, each clearing a cache word at `+0x118/+0x294/+0x29c`; vtable slot
  ro `0x166cd28`). The stored value is a product of two parameters (`fmul s3,s0,s1`), not a ratio; nothing
  projection-like reads it.
* `0x13ef948`: `+0xb0` = a libm call on `field*s8` - a trigonometric value.
* `0xe8b498` and `0x116e3f4..0x116e400`: a byte divided by `255.0` (ro `0x16afbb8`) - colour channels.
* `0x12d14e4`, `0x132db24`: a negated input component; `0xe8b544..0xe8b570`, `0x105d020..0x105d060`: `+0xac/+0xb4/+0xbc`
  differences divided by a common scale, not a tangent.
