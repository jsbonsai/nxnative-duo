## What this binary is (affects how the chain reads)

The module is **Hagi**, Nintendo's Wii-on-Switch runtime: rodata carries
`C:/Development/Nightly/Comet/Trunk/hagi/source/hagi/gekko/Gekko.cpp`,
`.../Flipper/flipper/VirtualFlipperGuestCommandProcessor.cpp`, `hagi/virtualmachine/VirtualMachine.cpp`,
`--generatetest`, `m_pGekko->Initialize(...)`, and RomFS (2.75 GB) holds the disc image. The camera and
projection code the patch touches is nevertheless **native aarch64 in this same main**: it names the game's
own camera types (`CAM_TYPE_ANIM`, `CAM_TYPE_WONDER_PLANET`, `CAM_TYPE_TRIPOD_PLANET`, `CAM_TYPE_CUBE_PLANET`,
`CAM_TYPE_MEDIAN_PLANET`, `CAM_TYPE_FOO_FIGHTER_PLANET` at ro `0x726ae2`, `0x72554c`, `0x705354`, `0x70be58`,
`0x718c0e`, `0x6fecb3`), it carries SMG2's projection constants (fovy 45°, near 100, far 800000) and its
result is uploaded as the GPU projection matrix (below). [INFERENCE] Whether that native camera is the whole
world render or a HLE replacement of the guest's camera cannot be settled from static code alone; the words
patched here are the ones this module uses to build and upload the scene projection.

## The chain

### 1. The aspect value: 812 / 456

* `0xe2bf0` returns the game's screen width:
  `0xb4be0: b 0xa5bd0`, `0xa5bd0: mov w0,#1; ret` → `tst w0,#1` is always true → `csel w0, w9, w8, ne`
  always picks `w9 = 0x32c = 812`. The 4:3 branch (`w8 = 0x260 = 608`) is dead in this build.
* `0x2fe5e0` (24 bytes) is **the aspect getter**:

```
0x2fe5e0  bl      0xe2bf0            ; w0 = 812
0x2fe5e4  scvtf   s0, w0
0x2fe5ec  mov     w8, #0x43e40000    ; 456.0f
0x2fe5f4  fmov    s1, w8
0x2fe5f8  fdiv    s0, s0, s1         ; <-- site 3: aspect = 812/456 = 1.7807018
0x2fe5fc  ldp / ret
```

  Its only entrance in the module is `0xe10d0`, which fetches the current camera object and tail-branches
  here (`0xe10d0: bl 0x1821f0; mov w1,#0x18; bl 0x18215c; b 0x2fe5e0`). There is no direct `bl 0x2fe5e0`.
* The same `812/456` is computed twice more, inline, in the camera:
  `0x2fe4a0` (inside `0x2fe470`, see below) and `0x2fe2e0` (inside the camera constructor `0x2fe200`,
  which caches it at `[camera+0xbc]`).

### 2. The camera object

`0x2fe200` constructs it: vtable from `[0xa098a0]+0x10`, `fovy [cam+0xc8] = 45.0` (`0x42340000`),
`[cam+0xc0] = 100.0 / [cam+0xc4] = 800000.0` (near/far, packed `0x4943500042c80000`), then
`0x2fe2e0 fdiv s0,s0,s1` → `str s0,[x19,#0xbc]`, then `bl 0x2fe470`.

Accessors used by everything else (`0x1821f0` → `[0x98a79178]` → `+0x48` → index `0x18` of a pointer array):

| getter | reads | meaning |
|---|---|---|
| `0xe0ec0` | `[cam+0xc8]` | fovy (degrees) |
| `0xe10f0` | `[cam+0xc0]` | near |
| `0xe1110` | `[cam+0xc4]` | far |
| `0xe10d0` → `0x2fe5e0` | — | aspect |
| `0x2fe5d0` | — | returns `cam+0x1c`, the 12-float view matrix |

Layout: view matrix at `+0x1c` (12 floats, `0x30` bytes), projection 4×4 at `+0x7c..+0xb8`,
cached aspect `+0xbc`, near `+0xc0`, far `+0xc4`, fovy `+0xc8`.

### 3. The two projection builders (both divide by this aspect)

`0x2fe470` — builds the camera's own 4×4 at `[cam+0x7c]`:

```
0x2fe488  ldr   s8, [x0, #0xc8]     ; fovy
0x2fe490  bl    0xe2bf0             ; 812
0x2fe4a0  fdiv  s11, s0, s1         ; <-- site 2: aspect (s1 = 456.0)
0x2fe4a4  ldp   s9, s10, [x19, #0xc0] ; near, far
0x2fe4a8  bl    0x57a3a8            ; 2*pi (fov deg -> rad)
0x2fe4b8  fdiv  s0, s0, s1 ; ... bl 0x6de630 (tanf)
0x2fe4e0  fdiv  s0, s1, s0         ; cot(fovy/2)
0x2fe4f0  fdiv  s2, s0, s11        ; m[0] = cot/aspect
0x2fe4f4  str   s2, [x0, #0x7c]!   ; projection at cam+0x7c
0x2fe4fc  str   s0, [x0, #0x14]    ; m[5] = cot
then near/far terms (0x2fe524..0x2fe534) and `bl 0x2fe698` (Mtx44 concat)
```

`0x2a5664` — the render pass's projection, built per draw from the getters and uploaded:

```
0x2a5694  bl 0xe0ec0   ; fovy
0x2a569c  bl 0xe10d0   ; aspect  (-> 0x2fe5e0)
0x2a56a4  bl 0xe10f0   ; near
0x2a56ac  bl 0xe1110   ; far
0x2a56b4  bl 0x57a3a8 ; ... 0x2a56c8 bl 0x6de630 (tanf)
0x2a56e8  fdiv s0, s1, s0   ; cot
0x2a56f0  str  s0, [sp, #0x44]   ; m[5]
0x2a56f4  fdiv s2, s0, s9       ; m[0] = cot/aspect   (s9 = aspect)
0x2a56fc  str  s2, [sp, #0x30]
0x2a5704..0x2a5710  near/far terms
0x2a5714  bl 0x5964f0           ; upload the 4x4 as the GPU projection
```

`0x2a5664` is the vtable method of the drawable: slot `0x92a0d8` = `0x2a55a0`, which calls `0x2a5664` and
then `0x25026c(..., 0)` and `0x25026c(..., 0x11)` (the two draw lists).

There are two more perspective builders that take the same aspect: `0x597a80` (called once from `0x3e4124`,
which builds a projection from fovy+aspect+0.5 and submits it through `0x548940`) and `0x15c34c` (called from
`0x15c000`). Neither uploads the scene projection; both would simply inherit the narrower ratio.

### 4. Proof the camera matrix is the GPU projection

`0x5964f0` writes the 12 floats at `x0` to the uniform block `[[0xa11ce0]+0x...]+0x4d8..0x4f0`
(`[x0] → +0x4d8`, `[x0+0x14] → +0x4e4`, `[x0+0x28] → +0x4ec`, `[x0+0x2c] → +0x4f0`; `w1` picks the
`+8`/`+0xc` column). Its 22 call sites include three that hand it the camera object's matrix directly:

```
0x18a6a0  bl 0x2fe5d0          ; cam+0x1c (view)
0x18a6b0  bl 0x597090          ; copy 12 floats of the view to 0x98a7d8d0
0x18a6b4  ldr x8, [x19, #0x38] ; the camera
0x18a6bc  add x0, x8, #0x7c
0x18a6c0  bl 0x5964f0          ; upload its projection
```

and `0x18b8d4` / `0x18b984` do the same with `[x19, #0x60]`. So the matrix built at `0x2fe4a0` is the
projection the scene is drawn with, and the one built at `0x2a5664` (from the getter) is the same camera's
projection for the other render path.

## The three sites

| offset | word | instruction | produces |
|---|---|---|---|
| `0x2fe2e0` | `1e211800` | `fdiv s0, s0, s1` (camera ctor `0x2fe200`) | `[cam+0xbc]` = aspect |
| `0x2fe4a0` | `1e21180b` | `fdiv s11, s0, s1` (`0x2fe470`) | aspect used for `m[0]` of `[cam+0x7c]` |
| `0x2fe5f8` | `1e211800` | `fdiv s0, s0, s1` (`0x2fe5e0`) | the aspect getter itself (`0xe10d0`) |

All three are the ratio in `s<d>` and nothing else, so the constant stub is exact: the sites drop a division
with no side effect and take `1.4215247` instead. Patching all three keeps every consumer consistent
(camera matrix, render-pass projection, cached field); patching only `0x2fe5f8` would leave the camera's
own `+0x7c` matrix — the one `0x18a6c0` uploads — at 16:9.

Nothing in this build is a rewrite site (`main.sites.tsv` has no entry at or near these offsets), and the
FAR layout puts the stubs at `PATCH_OFF = -0x2000000` (front patch area, `FRONT = 0x2000000`), which is
36.7 MB from `0x2fe4a0` — inside the `B` reach of ±128 MB.

## Rejected alternates (with the reason)

* **`0x2a56f4` `fdiv s2, s0, s9` (in `0x2a5664`)** and **`0x2fe4f0` `fdiv s2, s0, s11` (in `0x2fe470`)** and
  **`0x597b04` `fdiv s1, s0, s12` (in `0x597a80`)** — these are `cot(fovy/2)/aspect`, i.e. matrix element
  `m[0]`, not the ratio. A literal there would put 1.4215 in the matrix instead of ~1.698, a 19 % error.
  These three are the *consumers* of the sites above.
* **`0xe2bf0` / `0xa5bd0` (the width 812)** — it is the screen width, not the aspect: 65 callers use it for
  layout/scaling; patching it would move every one of them.
* **The fovy `45.0` at `0x2fe2b0`** — that is the `Vert+` route (widen the vertical FOV); the Duo fix must
  keep the vertical FOV and narrow the horizontal one.
* **`find_aspect.py`'s sead-looking `#0xb0` hits**: `0x2b37c0`, `0x336084`, `0x39472c`, `0x3e68ec`, `0x3e6950`,
  `0x3230b8`, `0x11b050`, `0x32c050`, `0x1f3bf4`, `0x2e2c98`, `0x2fba0c`, `0x2fd964`, `0x11b2cc`, `0x2e2c98`.
  None of their functions calls `0x5964f0` (projection upload), `0x597090` (view copy), `0x2fe470` or
  `tanf`; they are transform copies, light/cone maths and unrelated structs (e.g. `0x2b37c0` copies a
  12-float matrix pair into `+0xa8..+0xb4` — a sead-shaped layout, but not a camera this build
  projects with). Verified by scanning each containing function for those callees.
* **The 16:9 rodata constant** — there is none: the 32-bit `0x3FE38E39` occurs 0 times and the double
  `1.7777778` 0 times in the whole image (text+ro+data), which is why the row's column 3 is `-`.

## Framing and risk

With fovy 45°: 16:9 gives hfov `2*atan(1.7807*tan(22.5°)) = 72.8°`, the Duo ratio
gives `2*atan(1.4215*tan(22.5°)) = 61.0°` — the same picture as Crop, rendered at the full width.

Known side effects to look for on the first device run: `0x3e4124` builds a *separate* projection from
fovy+aspect (`0x597a80`, submitted via `0x548940`, mode 2) and `0x25d070` draws the view cone from the same
getter; both receive the narrower ratio. If a full-screen element (movie/screenshot quad) turns out to be
drawn through `0x3e4124` it would shrink horizontally; the fix then is to drop `0x2fe5f8` from the row and
keep `0x2fe2e0,0x2fe4a0` — but that would also leave the per-draw path `0x2a5664` at 16:9, so it needs the
screenshot test first (aspect.md §5).
