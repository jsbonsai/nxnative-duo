# DRAGON QUEST VII — the Duo aspect lever (canvas size)

Build `ab06020960edd8285b7ff5fad2e3224b` (v65536, `main` at
`/path/to/work/0100A9D01C446000_build/extract/v65536/ExeFS/main`).
Offsets are **image offsets**: text `0..0x4f8e9f0`, rodata `0x4f8f000..0x5819000`,
data `0x5819000..0x63cb748`.

**Result: the canvas size is not an immediate anywhere in `main`, so there is no canvas
patch for this build.** This file records what the size is, what it is *not*, and where
to look next. The projection lever stays the 16:9 rodata constant already registered for
this build (`duo/research/games.tsv`: `ab060209…  0x5183ddc`).

## 1. Engine and the log line

Unreal Engine 4 (the image carries UE4's UTF-16 config/name blob and
`RHICreateTexture2D`-shaped calls). `[nvn] WindowInitialize … first WxH`
(`dm/gfx/nvn/hle_nvn.c:1290`) prints the first swap-chain texture's dimensions, i.e. what
the guest passed to the NVN texture builder.

NVN is resolved by name at startup into **two** proc tables (two devices), page `0x7f77000`
and `0x7f78000`. Verified slots (device 1):

| slot | proc |
|---|---|
| `0x7f774c8` / `0x7f774d0` | `nvnWindowBuilderSetDevice` / `SetDefaults` |
| `0x7f774d8` / `0x7f774e0` | `nvnWindowBuilderSetNativeWindow` / `SetTextures` |
| `0x7f77528` | `nvnWindowInitialize` |
| `0x7f77780` / `0x7f77788` | `nvnTextureBuilderSetWidth` / `SetHeight` |
| `0x7f777a0` | `nvnTextureBuilderSetSize2D` |
| `0x7f78850` | `nvnTextureBuilderSetSize2D` (device 2, **never called**) |

## 2. The swap-chain path, end to end

```
0xe00798  wrapper: malloc(0x650) then the ctor
0xe0080c  ctor(this, x1, w2=width, w3=height, w4=flag)
0xe0085c      str d1,[x0,#0x208]      ; cache width/height at +0x208/+0x20c
0xe00b5c  resize(this, w1=width, w2=height, w3=flag)
0xe00b5c      ldr w8,[x0,#0x208]; cmp w8,w1
0xe00b68      ldr w9,[x0,#0x20c]; ccmp w9,w2,#0,eq   ; unchanged → return
0xe00c70      bl 0x287390                             ; allocate the texture object
0xe00c74      mov w1,#0x25                            ; NVN format 0x25
0xe00c78      mov w2,w21   ; width   ← function argument
0xe00c80      mov w3,w28   ; height  ← function argument
0xe00c84      mov w4,#1; mov w5,#1; mov w6,#1; movk w6,#2,lsl #16; mov x7,xzr
0xe00ca0      bl 0xe00f58                             ; build one swap-chain texture
0xe00d40 … 0xe00d94   nvnWindowBuilderSetDefaults/SetDevice/SetNativeWindow
0xe00d64 … 0xe00d78   nvnWindowBuilderSetTextures(builder, [this+0x688], array)
0xe00d94 …            nvnWindowInitialize
```

`0xe00f58` is the descriptor fill: `stp w2, w3, [x0, #0x58]` writes **width at `+0x58` and
height at `+0x5c`** of the texture descriptor, then tail-calls `0x66f9f8`, which is the
function that reaches `nvnTextureBuilderSetSize2D` through the proc table
(`0x4d98904`, `0x4d98ac4`, both inside the generic builder `0x4d98844` with `w1`/`w2` from
its own arguments).

So the size is a **value flowing through arguments**, and every instruction that consumes it
loads it from a register or a struct field. Nothing in the chain is an immediate.

## 3. What the size is *not* (the exhaustive search)

The canvas patch needs a `movz`/`mov #imm` (or a rodata pair) that the swap chain reads.
None exists:

* **Every 1920 materialisation in text** (7 sites): `0xc0eaf0` (`mov w4,#0x780`, one
  argument to the runtime helper `0x4c890`), `0xf07720` (`mov x9,#0x780` +
  `movk x9,#0x438,lsl #32`, a default stored into a pixel-format/shader-platform object at
  `[x19+0x234]` in a function that dispatches on a format id), `0xfe1a34` (§ below),
  `0x3190cd0`/`0x3190cdc` (a debug/format struct, 1920 twice), `0x489ba5c`
  (`memset(ptr,0,1920)`), `0x4e10824` (`mov w4,#0x780`, one argument to `0x1d2e630`).
* **Every 1080 materialisation in text** (61 sites): none is a size argument to a call
  with a 1920/1280 partner; the argument-register ones are `malloc(1080)`, log strings,
  format-struct inits and `memset` lengths.
* **No `w1`/`w2` (or any two-register) pair of 1920×1080 or 1280×720 exists** in text, and
  no 1920 and 1080 immediates occur within ±400 bytes of each other except the pair below.
* The one adjacent 1920/1080 argument pair, `0xfe1a30`/`0xfe1a34`, is
  `RHICreateTexture2D(SizeX=1920, SizeY=1080, Format=PF_B8G8R8A8=2, Mips=1, Samples=1,
  Flags=TexCreate_RenderTargetable=1)` through the RHI vtable slot `[x8+0x590]`. Its result
  is pushed into a UI/resource list (`0x75a7c0`, `0x17f9a0`) and never reaches the swap
  chain.
* The rodata pairs `{1280,720}` at `0x518c1e8` and `{1920,1080,2560,1440}` at `0x518da30`
  have **no reader at all**: no `adrp`+`add`/`ldr` reaches them and no pointer to them
  exists in the image. (`1920.0f` at `0x518bde8` is likewise unread.)
* The game **does not import** `nn::oe::GetDefaultDisplayResolution` — the `DT_JMPREL`
  table lists only `GetOperationMode`, `GetPerformanceMode`, `GetDesiredLanguage`,
  `GetCurrentFocusState`, `TryPopNotificationMessage`, the notification enables,
  `SetPerformanceConfiguration`, `SetCpuBoostMode`, `ExecuteProgram`, … The 12
  `GetOperationMode` call sites (`0x837d64`, `0xb470d8`, `0xd70d20`, `0x2440bd0`,
  `0x2440dd0`, `0x2441080`, `0x244121c`, `0x3452024`, `0x3452280`, `0x34523a0`,
  `0x34535a4`, `0x4633fc8`) pick **quality floats**, not sizes — e.g. `0x837d64` loads
  `0.03f` from `0x51837d8` and `fcsel`s against it by mode.
* The `nn::vi` imports are only `Initialize`, `OpenDefaultDisplay`, `GetDisplayVsyncEvent`,
  `CreateLayer`, `GetNativeWindow` — there is no resolution query.

## 4. Where to look next, in order

1. **Runtime, cheapest:** log the `(w2,w3)` that reaches `0xe00798`/`0xe0080c` (one `LOG`
   at the ctor, or a breakpoint on `0xe00b5c`), then walk one frame up the call stack. The
   value is passed, so a backtrace names its producer immediately.
2. **The virtual caller.** The swap-chain ctor is reached through the RHI interface: the
   pointer `0xe00798` sits at rodata `0x6305380` and **nothing in the image references that
   address** (no `adrp`+`add`, no relocation), so the vtable is installed at run time.
   Find the object whose vtable base is `0x6305380` and you find `FSwitchRHI`'s
   swap-chain creation, i.e. the width/height source.
3. **UE4's window/viewport.** `FSwitchViewportSwapChain` takes its size from the window.
   Since this build never asks `nn::oe`/`nn::vi` for a resolution, the number is either a
   UE4 config value or a constant materialised in a form this scan does not model (e.g.
   built from a float by `fcvtzs`). The config candidate is
   `[/Script/Engine.GameUserSettings] ResolutionSizeX/Y`, which lives in the game's RomFS
   (`extract/v65536/RomFS.img` is present but has not been extracted here — extract it and
   look for a `.ini` before assuming the size is code); the constant candidate needs a
   runtime watch (step 1).
4. Until one of those lands, the **16:9 constant `0x5183ddc`** (already a `duo/research/games.tsv`
   row for this build) is the only lever: it fixes the projection aspect, not the canvas.

## 5. If a size site is found later

Apply the same rule as the other two games: patch **heights only**, keeping the width, so
the horizontal pixel scale stays 1:1 —

* `1080 → 1350` (`movz` immediate `0x438 → 0x546`; packed pairs: `movk …, #0x546, lsl #32`)
  for 1920-wide canvases,
* `720 → 900` (`0x2d0 → 0x384`) for 1280-wide canvases,

and patch **both** the display/render size and the swap-chain texture size, or the picture
is squeezed by the game's own blit. 1920×1350 = 1.42222 against the Duo's 2853×2007 =
1.42152.

come from `DT_JMPREL` (tag 23) in the dynamic section.
