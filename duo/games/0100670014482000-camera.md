# Assassin's Creed: The Ezio Collection — camera aspect chain (build `824b38a25986b2abf5b3a356430ee6b3`)

Target: `/path/to/work/0100670014482000_build/extract/v196608/ExeFS/main`
(NSO0, image `text 0x1f2e5e0 | ro 0x1f2f000+0xc95880 | data 0x2bc5000+0x96c248`, build id
`824b38a25986b2abf5b3a356430ee6b300000000`). All addresses below are offsets in the **module image**
(the same address space `patch_nso.py` cuts), not file offsets.

Verdict up front: **the 16:9 aspect is never materialised as a float the duo_aspect rewriter can patch.**
There is no 16:9 float in rodata at all, the only `1.7777778` literals are `movz/movk` register
immediates, and the one place 16:9 couples into a *camera angle* is an `fmul` of that immediate — not an
`fdiv` or an `ldr s`, the two instruction forms `dm/tools/duo_aspect.py` accepts. The registry row
therefore carries `-`/`-`; section 6 records exactly what would unlock a real site.

## 1. What the engine is, and the anchors that identify it

Anvil/Scimitar (the AC2 engine), statically linked with the NintendoWare SDK. Confirmed by the debug /
reflection strings, which are the only symbol-quality evidence in the module:

| string | address | meaning |
|---|---|---|
| `Aspect_Full`, `Aspect_4x3`, `Aspect_16x9`, `Aspect_16x9_in_4x3`, `Aspect_Custom` | `0x2527d14`, `0x25383e8`, `0x2572612`, `0x253c9c9`, `0x2523ad7` | the `DisplayOptions::AspectRatio` enum |
| `DisplayOptions::AspectRatio` | `0x2548c32` | the property |
| `PositionMode_AspectRatioCenter` | `0x257664e` | how the picture is placed in the display |
| `fovyDegrees` | `0x2542cf6` | animatable camera FOV (degrees) |
| `FIXEDTRACKID_CAMERA_FOV` | `0x254d9fb` | camera track id |
| `View::ProjectionType` | `0x2559379` | view property |
| `g_ReverseProjectionParams` | `0x261960b` | renderer-side inverse-projection params |
| `nvnCommandBufferSetViewport(s)` | `0x255c129`, `0x2570e93` | nvn viewport calls |
| `resolutionWidth` / `resolutionHeight` | `0x250deaa` / `0x2558389` | config property names |

The enum's descriptor table sits at rodata `0x20f5540`, one 0x18-byte record per value
`{name_ptr, data_ptr, 0x403}`:

```
20f5540  0x2527d14  Aspect_Full
```

## 2. No 16:9 constant exists in the image

Scan of the whole module image for the 32-bit float `0x3FE38E39` (1.7777778f):

```
16:9 occurrences: 0
```

There are also **no** `u32 1920`/`1080` pairs and no `1920.0f`/`1080.0f`/`960.0f`/`540.0f`
(`n = 0` each) anywhere in rodata/data. The resolution is therefore not a data constant either.

1920/1080 do appear as *immediates in UI code clusters*, which shows the app assumes a 1920x1080
canvas without storing it:

* `0xc6f3b8`, `0xc6f40c`, `0xc6f460`, `0xc6f568`, `0xc6f5bc`, `0xc6f80c`, `0xc6f868` — `mov w0,#0x780`
  (`mov w22,#0x438` = 1080 at `0xc6f398`; `mov w23,#0x21c` = 540 for the `0x3c0`=960 pairs) feeding
  `bl 0xaee708` then `bl 0xc5fad4`: creation of 1920x1080 and 960x540 UI/off-screen surfaces;
* `0xcd9498`, `0xcd9510`, `0xcd9584`, `0xcd9600` — the same pattern in a second function;
* `0x81f048` — the only `mov w0,#0x438`, a size argument next to string `0x256d447`.

None of these clusters contains a `fdiv` (`0xc6e000..0xc70800`: zero `fdiv`; `0xcd8000..0xcda800`:
only the rect-fit divisions in section 3), so the canvas size never becomes an aspect there.

## 3. Every real `1.7777778` literal, and what it does

The only way 16:9 exists in this module is as a *register immediate pair* `movz w,#0x8e39` plus
`movk w,#0x3fe3,lsl#16` (11 complete pairs). Each one is followed by `fmov sN,w`:

```
0x8bbc08/0xc   0xb40400/0x4   0xc3d244/0x8   0xc3d348/0xc   0xc449b8/0xc
0xc5101c/0x20  0xcd9174/0x78  0xcda434/0x38  0xff4ef0/0x4   0x11afa6c/0x70
0x11afcb4/0xb8
```

Ten of them are instantiations of one "fit a rectangle to a content aspect" template. Full body,
`0x8bbc00` (the others differ only in the destination base register and one constant register):

```
08bbf4  fmov s2, #0.56250000      ; 9/16
08bbf8  fmul s2, s1, s2           ; h * 9/16
08bbfc  fcmp s0, s2               ; w < h*9/16 ?
08bc00  mov  v3.16b, v1.16b
08bc04  b.gt 0x8bbc1c
08bc08  mov  w8, #0x8e39          ; 1.7777778f
08bc0c  movk w8, #0x3fe3, lsl16
08bc10  fmov s2, w8
08bc14  fmul s3, s0, s2           ; w * 16/9
08bc18  mov  v2.16b, v0.16b
08bc1c  fsub s4, s1, s3           ; h - ...
08bc20  fsub s5, s0, s2
08bc24  fmov s6, #0.5
08bc28  fmul s4, s4, s6
08bc2c  fmul s5, s5, s6
08bc30  fdiv s4, s4, s1           ; -> normalised crop, +0x70
08bc34  fdiv s5, s5, s0
08bc38  stp  s4, s5, [x19, #0x70]
08bc3c  fdiv s1, s3, s1           ; -> +0x78
08bc40  fdiv s0, s2, s0
08bc44  stp  s1, s0, [x19, #0x78]
```

That is the `DisplayOptions::AspectRatio` / `PositionMode_AspectRatioCenter` picture-rect fitter
(pillarbox/letterbox maths): it produces a *screen rect*, not a projection. Patching it would change
HUD/cutscene placement, not the 3D world — the opposite of what section 2 of `duo/design/aspect.md`
wants.

The eleventh site is different, and is the only place where 16:9 touches a camera *angle*:

```
0xff4ee0  ldr  s0, [x21, #0x34]    ; fovy (rad)
0xff4ee4  fmov s10, #0.5
0xff4ee8  fmul s0, s0, s10         ; fovy/2
0xff4eec  bl   0x1f2c580           ; trig kernel (sin/asinf family)
0xff4ef0  mov  w8, #0x8e39         ; 1.7777778f
0xff4ef4  movk w8, #0x3fe3, lsl16
0xff4ef8  fmov s1, w8
0xff4efc  fmul s0, s0, s1          ; <-- vertical angle -> horizontal, assuming 16:9
0xff4f00  bl   0x1f2d020
0xff4f04  fadd s0, s0, s0          ; *2  (full hfov)
0xff4f08  fmul s0, s0, s10         ; /2
0xff4f0c  bl   0x1f2c580
0xff4f10  mov  w8, #0xf5c3
0xff4f14  movk w8, #0x41a0, lsl16  ; 20.0f
0xff4f18  fadd s0, s0, s0
0xff4f1c  fmov s1, w8
0xff4f20  mov  w8, #0x6ead
0xff4f24  movk w8, #0x3c75, lsl16  ; 0.0149xx
0xff4f28  fmov s2, w8
0xff4f2c  mov  w8, #0xa5e3
0xff4f30  movk w8, #0x3c9b, lsl16  ; 0.0189xx
0xff4f34  fdiv s0, s1, s0          ; 20 / tan(hfov/2)  -> "lens"/zoom
0xff4f38  fmul s1, s0, s0
0xff4f3c  fdiv s0, s0, s2
0xff4f40  fmov s2, w8
0xff4f44  fmul s3, s0, s2
0xff4f48  fdiv s1, s1, s3
0xff4f4c  fcmp s9, s1
0xff4f58  fadd s0, s9, s1          ; defocus/CoC blend (rational form)
0xff4f60  fdiv s0, s2, s0
0xff4f64  fdiv s1, s2, s1
0xff4f88  stp  s1, s8, [x23, #0x30]
0xff4f94  str  s2, [x23, #0x2c]
0xff4f98  stp  s0, s9, [x23, #0x24]
0xff4f9c  str  wzr, [x23, #0x38]
0xff4fa0  str  s8, [x23, #0x3c]
```

So this engine derives the horizontal FOV from the (track-animated) vertical `fovyDegrees` by scaling
with a hard-coded 16:9 and then storing lens/CoC parameters. That is the aspect coupling the Duo
method wants to change — but the value arrives in `s1` from `movz/movk`, and the only arithmetic that
touches it is `fmul`. **`duo_aspect.form_ok()` accepts only `fdiv s<d>,s<n>,s<m>` (0x1e201800 mask) and
`ldr s<d>,[x<n>,#imm]` (0xbd400000 mask); it cannot express this site.** There is likewise no `fdiv` by
the reciprocal form (divide by 9/16 = 0.5625): the "fdiv with a 0.5625 divisor" scan returns 0.

## 4. The projection builder is on the CPU, and the one found is orthographic

To be sure the relevant maths is in this module and not in `sdk`, the matrix builders were located by
their store signature (`str s,[x,#0x0], [x,#0x14], [x,#0x28], [x,#0x2c], [x,#0x38], [x,#0x3c]`).
58 such groups exist. One is a complete, self-contained projection builder:

```
0xc4f920  stp d11,d10,[sp,#-0x50]!          ; x1,x2 = rect ptrs, x3 = float4x4 out, s0,s1 = near,far
0xc4f944  ldp s0, s1, [x2]                  ; rect B
0xc4f948  fmov s4, w8      ; w8 = 0x3a800000 (1/1024)
0xc4f94c  ldp s2, s3, [x1]                  ; rect A
0xc4f954  fmul s10, s0, s4                  ; (Bx-Ax)/1024
0xc4f95c  fmul s11, s0, s4                  ; (By-Ay)/1024
0xc4f9e0  fsub s1, s8, s9                   ; near - far
0xc4fa1c  fdiv s5, s4, s5                   ; 2/(r-l)
0xc4fa24  fdiv s2, s4, s2                   ; 2/(b-t)
0xc4fa2c  str  s5, [x19]                    ; m00
0xc4fa30  str  s2, [x19, #0x14]             ; m11
0xc4fa34  str  w8, [x19, #0x3c]             ; m33 = 1.0f
0xc4fa38  fdiv s4, s6, s1                   ; 1/(near-far)
0xc4fa3c  str  s4, [x19, #0x28]             ; m22
0xc4fa40  fdiv s1, s8, s1                   ; near/(near-far)
0xc4fa44  str  s1, [x19, #0x38]             ; m32
0xc4fa50  stp  s0, s1, [x19, #0x30]         ; m30, m31 (offsets)
```

That is `glOrtho` (2/w, 2/h, 1/(near-far)) with a 1/1024 rect scale, i.e. the CPU does build these
matrices natively — but no *perspective* sibling with a 16:9 or a viewport-derived divisor exists
among the 58 groups: there is no `str` of -1.0f to `[x,#0x2c]` anywhere in `.text` (0 hits), which
every conventional perspective matrix needs.

| `0xff4ef0` | `mov/movk 16/9` | real vertical-to-horizontal FOV coupling, but `movz/movk`+`fmul` — `duo_aspect.form_ok()` rejects it |
| `0xff4f34` | `fdiv s0,s1,s0` (20.0 / tan) | zoom/defocus ratio, not the ratio itself; `s0` is already the 16:9-scaled angle |
| `0x13e4b4`, `0x13e6cc`, `0x13e7f0` | `fdiv s0,s0,s1` near `#0xac`/`#0x38`/`#0xb0` | `(new-old)/frames` camera-parameter interpolator at `0x13e3cc`; the `#0xb0`/`#0xac` coincidence is a parameter slot, not a sead projection field |
| `0x6aeac`, `0x6aef0` | `fdiv` inside `fsqrt`/trig block at `0x6ae60` | quaternion to 3x3 matrix (stores at `+0x1c..+0x40`), not a projection |
| `0x494c88` | `fdiv s10,s11,s10` | spline/Bezier interpolation (`bl 0x1f2ca40` chain), not a projection |
| `0xc4f920` | ortho builder (section 4) | `2/(r-l)`, `2/(t-b)`, `1/(near-far)`: orthographic, no aspect term |
| `0xc4f6e0` region | `fdiv` cluster | 4x4 inverse/adjugate helper, not a projection |
| 564 "same-base fdiv" candidates | various | engine-wide vec2 divisions; two loads from one struct are not evidence of aspect |
| 407 "1.0/x" fdiv candidates | various | reciprocals/lerps throughout animation and collision code |

The `DisplayOptions::AspectRatio` *enum* is real (table at `0x20f5540`), but the value it selects is
consumed by the rect fitter of section 3, i.e. it drives where the picture is placed, not the camera's
projection.

## 6. Why there is no registrable site, and what would unlock one

* `dm/tools/duo_aspect.py` sites are `fdiv s<d>,s<n>,s<m>` or `ldr s<d>,[x<n>,#imm]` and the stub
  substitutes the drawable ratio in the site's `s<d>`. This build produces 16:9 exclusively as a
  `movz/movk` immediate pair followed by `fmov`+`fmul`, and it produces the projection from a viewport
  rect that is built at run time (no 1920/1080 and no 1.7777 anywhere in the data segments).
* Nothing here can be replaced without either (a) adding a third patch kind to
  `dm/tools/duo_aspect.py` that recognises the `movz w,#0x8e39` / `movk w,#0x3fe3` pair (and the
  matching `0x8e38`/`0x3ce3`-style near-1.777 variants), or (b) finding the caller that hands the
  horizontal FOV / aspect into the perspective matrix, which is not statically derivable from this
  module because the value originates outside it.
* No `nx build --prepare-xcode` was run: there is no row to apply, so there is no rewrite line or
  `main.cuts.tsv` output to quote.

Recommended next step: dump `0xff4e00-0xff5000` at run time (or find the object written at
`x23+0x24..0x3c` and its readers) to confirm the horizontal FOV from `0xff4ef0` is what the perspective
matrix consumes; if so, extend `duo_aspect` with a `movz/movk` site kind and register `0xff4ef0`.
