# Demon Slayer: The Hinokami Chronicles — `0100309016E7A000` — camera aspect

Build: **`14c878ecca9d7cb5b57e9b492b1bdb92`** (module ID, NSO header +0x40; the same 16 bytes the tools key on).
Module `main`: 59.6 MB in the file, image `text 0x0+0x5cc28a0` · `ro 0x5cc3000+0x2979418` · `data 0x863d000+0xc0ff78` · `bss 0x2daf088`.
Extracted at `/path/to/work/0100309016E7A000_build/extract/v589824/ExeFS/main`; the RomFS exists only as a 9.8 GB `RomFS.img`.

**Result: no camera-aspect word is registered.** The engine is Unreal Engine 4, and UE4 keeps no 16:9 float: it
derives the aspect from the view rectangle at run time. The only three instructions in the whole 97 MB of text that
perform that derivation were found (below); two are unreachable in this build and the third feeds a render pass,
not the camera projection. The projection builder itself was not located, so the row is `-` / `-` (the LM3
precedent) rather than a guess.

* The renderer data the code in §3 walks: view family at `x28` with `count = [x28+0xa8]`, `views = [x28+0xa0]`,

  `UnscaledViewRect` is at `+0x258..+0x264` (`MinX, MinY, MaxX, MaxY` as ints) with flags at `+0x280`, `+0xad0`,
  `+0xd7a`, `+0xd7c`, `+0x51ec`. Nothing here is sead/NintendoWare.

## 3. The only view-rect -> aspect computations in the module

`duo/tools/find_aspect.py`'s scoring is meaningless here — it looks for the sead projection fields
(`str s,[x,#0xac]` / `[x,#0xb0]`), and there is **not one such store** in this module. A data-flow scan works
instead: of the module's **11,919 `fdiv s<d>,s<n>,s<m>`** and **130,770 `ldr s<d>,[x<n>,#imm]`**, only **58**
`fdiv`s divide one `scvtf` by another, and exactly **three** divide `(float)(MaxX-MinX)` by `(float)(MaxY-MinY)`
of the `FSceneView` rect above. All three are the same word, `0x1E211800` = `fdiv s0, s0, s1`, which the
rewriter accepts (`(ins & 0xffe0fc00) == 0x1e201800`):

```
0x3b084b0  ldr w8,[x1,#0x260] ; ldr w9,[x1,#0x258] ; sub w8,w8,w9      ; width  = MaxX-MinX
           ldr w9,[x1,#0x25c] ; scvtf s0,w8
           ldr w8,[x1,#0x264] ; sub w8,w8,w9 ; scvtf s1,w8            ; height = MaxY-MinY
           ldr w8,[x1,#0x280] ; str w8,[x0]                           ; flag from view+0x280
0x3b084ec  fdiv s0, s0, s1                                                <-- SITE 1
           str s0,[x0,#4]                                             ; +4 = aspect, then +8 width, +0xc height
```

```
0x3b08610  (x1 = view, x2 = dst)  ... same four loads / sub / scvtf ...
0x3b08674  fdiv s0, s0, s1                                                <-- SITE 2
           str s0,[x19,#0x64]                                         ; +0x60 flag, +0x64 aspect, +0x68 width, +0x6c height
```

```
0x3b0a074  fdiv s0, s0, s1                                                <-- SITE 3
0x3b0a078  str s0,[sp,#0x254]                                           ; sp+0x250 flag, +0x254 aspect, +0x258 width, +0x25c height
```

The shape is unmistakable: each site produces the width/height float that is stored beside the rect's width and
height in a `{int flag, float aspect, float width, float height}` record.

## 4. Why none of the three is the live camera word

**Sites 1 and 2 are unreachable in this build** (the rewriter would still accept them, so this was checked):

* no `b`, `bl`, `b.cond`, `cbz/cbnz`, `tbz/tbnz` in text has target `0x3b084b0` or `0x3b08610` (every branch form
  decoded over all 24.3 M text words);
* no `R_AARCH64_RELATIVE` addend equal to either entry among the **1,158,058** RELA records of the MOD0 dynamic
  table, so they are in no vtable or function-pointer table either.

They are outlined copies the linker kept; patching them cannot change anything at run time.

**Site 3 is live but renderer-side.** `0x3b0a074` sits in the per-view loop of a render-setup function that starts
at `0x3b09800` (`stp x29,x30,[sp,#0x80] ; add x29,sp,#0x80 ; sub sp,sp,#0x420`) and runs to ~`0x3b0c8xx`:

* it walks the family's views (`count = [x28+0xa8]`, `views = [x28+0xa0]`, stride `0x5a20`) testing
  `[view+0x19fc]`, `[view+0x51ec]&1`, `[view+0xd7a]`, `[view+0xad0]`, `[view+0xd7c]`;
* the branch bodies at `0x3b0a0a4` / `0x3b0a100` re-read those same flags — this is `FViewInfo`, not a camera;
* the aspect goes into a stack descriptor (`sp+0x250/0x254/0x258/0x25c`) that is handed to a **virtual call on the
  RHI/command-list object** (`[0xb1b8000+0xbc0]`, method `[x8+0x108]`, `x2 = sp+0x110`, at `0x3b0a164..0x3b0a184`),
  then a command-buffer helper `0x3cd7d60(scene+0x31b0, 0, cmdlist)` at `0x3b0a198`.

That is a per-view pass input, not the projection. Registering it would at best be a no-op and at worst
de-synchronise a screen-space pass from the projection — the failure mode `duo/design/aspect.md` §2 warns about,
where depth + screen UV are combined with the *unscaled* inverse projection.

## 6. What was not resolved (the actual gap)

* **No `1/tan` anywhere.** Of the 2,504 calls landing in the libm tail (`0x5cbf000..0x5cc28a0`), none is followed
  within 80 instructions by both an `fdiv` and a matrix-element store, and none divides `1.0f` by a call result
  (0 sites). An inlined `FPerspectiveMatrix` with `FMath::Tan` would show exactly that, so the tangent is
  precomputed (a struct field or a table) or `tanf` lives outside that tail.
* **No aspect divisor.** A `fdiv` whose divisor is the aspect loaded from `+0x04` / `+0x64` / a stack slot: 76
  sites scanned, only one (`+0x64`) and it is the depth helper above. The aspect is consumed by a multiply or by
  a callee — site 3's callee is the RHI virtual.
* **Direction is unproven, and it matters.** UE4's `FPerspectiveMatrix` keeps the X FOV and scales Y by `h/w`
  (`MaintainXFOV`); the Duo needs the *inverse* of the drawable ratio there. The registry's constant stub writes
  the drawable ratio itself, which only fits a site that multiplies by `w/h` (`MaintainYFOV`). Nothing found
  establishes which form this game's FOV path takes, so even a located projection site has to be read for that
  before it is registered.

**Next step:** find `FSceneView::FSceneView` / `ULocalPlayer::GetProjectionData` — the function that writes the
per-view rect at `+0x258..+0x264` *and* a 16-float matrix — or identify `tanf` by its callers and walk up to the
projection. The three words in §3 are the only aspect materialisations to compare against.
`duo/games/0100309016E7A000.md` still records the shader-split blocker, so nothing can be verified on the device
before that is solved.
