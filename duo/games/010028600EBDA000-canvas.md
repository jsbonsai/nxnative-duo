# Super Mario 3D World + Bowser's Fury — the Duo canvas lever

Build `891687f016a18f1773d4a88ebf8a973c` (v262144, `main` at
`/path/to/work/010028600EBDA000_build/extract/v262144/ExeFS/main`).
All offsets below are **image offsets** (text `0x0..0x9c4a80`, ro at `0x9c5000`
size `0x8a2ee4`, data at `0x1268000` size `0x1b8e98`, bss `0x731168`), i.e. what
`patch_nso.py` rewrites and what `duo/research/res.tsv` numbers.

## 0. Why the 16:9 rodata constant is not the answer

`duo/research/games.tsv` registers the 16:9 float at `0xda6934` for this build, and
`duo/games/010028600EBDA000-aspect.txt` lists seven camera candidates. Both act
*after* the canvas exists: the game still renders 1920x1080 and the present pass
compresses that into the Duo's 2007x2853. Resizing the canvas removes the
compression entirely, which is why it is the lever to prefer.

## 1. A `movz` scan finds nothing — the size is a 64-bit immediate

A scan of every `movz`/`movk` immediate in text finds `1920` exactly once
(`0x8a8690 mov w0,#0x780`) and `1080` three times, and **no adjacent
`mov w,#0x780` + `mov w,#0x438` pair**. The whole-image scan for a u32 pair
`{1920,1080}` finds it only in the UI layout table at `0x13e7c48`
(`{1920,1080,1280,720,5, …}` — an entry per supported render resolution, read by
the UI scaler at `0x8023e0`), not in any canvas path.

The size is instead built as one 64-bit value holding two floats:

```
0x40b884  mov  x8, #0x44f00000        ; 1920.0f  (low half)
0x40b890  movk x8, #0x4487, lsl #48   ; 1080.0f  (high half)
0x40b898  str  x8, [sp]               ; {1920.0f, 1080.0f}
0x40b89c  bl   #0x711a80              ; agl Display::initialize(alloc, size)
```

That is why a `movz`-only scan misses it: the height is the `movk` half.

## 2. The chain, end to end

`0x40b690` is the game's graphics bring-up (`nn::account::Initialize`,
`nn::oe::Initialize`, renderer construction, display creation). It builds a
display config on the stack and fills two representations of the same 1920x1080:

| what | where | value |
|---|---|---|
| config ints, stored at `sp+0x44` (`movz x28,#0x780` / `movk x28,#0x438,lsl#32` at `0x40b818`/`0x40b81c`) | passed to the agl display ctor (`0x96ae90` → `0x711930`, x1 still live) | `1920, 1080` |
| size argument `x2` | `0x40b884`/`0x40b890`, `bl 0x711a80` | `1920.0f, 1080.0f` |

The base ctor copies the config word for word (`0x711958`…`0x71196c`): `config+0x10`
lands at `display+0xb0`, so the pair at `config+0x14` is exactly
`display+0xb4`/`+0xb8` — the ints the display init turns into the floats at
`+0x120`/`+0x124` (`ucvtf` at `0x711b7c`/`0x711b84`). So both representations of
the 1080p canvas are the ones patched below.

`0x711a80` is the agl display init: it calls `nv::InitializeGraphics`,
`nn::vi::Initialize`, `OpenDefaultDisplay`, `CreateLayer`, `GetDisplayNativeWindow`,
`nvnBootstrapLoader`, and it stores the passed pair verbatim:

```
0x711b78  ldr  w8, [x21]          ; 0x44f00000 = 1920.0f
0x711b80  str  w8, [x19, #0x110]
0x711b88  ldr  w8, [x21, #4]      ; 0x44870000 = 1080.0f
0x711b98  str  w8, [x19, #0x114]
```

`0x110`/`0x114` are the width/height of the agl **window sub-object that lives at
`this+0x108`** (its `+8`/`+0xc`). The same init writes the rest of that sub-object
in the same place: `+0x10` = nvn window (`str xzr,[x19,#0x118]`, later
`nvnWindowInitialize`), `+0x28` = texture array (`+0x130`), `+0x40` = vi native
window (`+0x148`), `+0x48`/`+0x49` = present interval and texture count
(`+0x150`/`+0x151`).

The swap-chain builder is `0x719970`. Its first instructions are the whole story:

```
0x719990  ldp   s0, s1, [x0, #8]     ; the pair stored at +0x110/+0x114
0x719998  fcvtzu w8, s0              ; width
0x7199a0  fcvtzu w8, s1              ; height
...
0x719a50  mov   w1, w23              ; width
0x719a54  mov   w2, w19              ; height
0x719a58  blr   x8                   ; nvnTextureBuilderSetSize2D
...
0x719d10  ...  nvnWindowBuilderSetTextures(this+0x49 count, this+0x28 array)
0x719d44  ...  nvnWindowInitialize(this+0x10)
```

`nvnTextureBuilderSetSize2D` is resolved once at `0x67d660` into the global at
`0x1a26f50` (GOT slot `0x141ac10`); `0x719a40` is the only code that calls it for
the swap chain. So the texture size the host prints in
`WindowInitialize … first WxH` is exactly the float pair at `0x40b884/0x40b890`.

Note what is *not* in this path: no `nn::oe::GetDefaultDisplayResolution` import
(the host answers 1920x1080, but this game never asks), no `nn::vi` resolution
query. The 1080p canvas is hard-coded, which is what makes it patchable.

## 3. The patch

Width stays 1920; the height becomes 1350 (1.42222, against the Duo's
2853x2007 = 1.42152 — 0.05 % off, the tolerance `duo/DESIGN.md` already accepts).

| offset | original word | new word | meaning |
|---|---|---|---|
| `0x40b890` | `0xf2e890e8` `movk x8, #0x4487, lsl #48` (1080.0f) | `0xf2e89508` `movk x8, #0x44a8, lsl #48` (1350.0f) | display size argument → swap-chain texture height |
| `0x40b81c` | `0xf2c0871c` `movk x28, #0x438, lsl #32` (1080) | `0xf2c0a8dc` `movk x28, #0x546, lsl #32` (1350) | the same canvas as ints in the display config (feeds the display's own `+0xb4/+0xb8` → `+0x120/+0x124` floats) |

`1350.0f` is `0x44a8c000`; the low half of the pair stays `0x44f00000` (1920.0f),
so only the `movk` immediate changes in each row. Both rows are asserted before
writing (`install_res` in `dm/tools/duo_aspect.py:78` compares two words and only
writes the first), so a different build fails the build instead of producing a
half-patched image; the asserted neighbour is the next instruction, unchanged.

Why both: the float pair is the canvas the swap chain is built from (proved in
§2); the int pair is the same canvas as the display config sees it, which becomes
the display's `+0x120/+0x124` and drives anything laid out against the screen.
Leaving the ints at 1080 while the canvas is 1350 would lay the HUD out for a
16:9 screen inside a 1.4222 canvas — the same mismatch that made Scott Pilgrim
need four rows (`duo/games/0100394011C30000-unity.md` §6).

Do **not** patch `0x8a8730`/`0x8a8750` (factories returning `{1920.0f,1080.0f}`
and `{1280.0f,720.0f}`) or the getters at `0x8a8690`–`0x8a8700`: none of them has
a `bl`/`b`, an `adrp`+`add`, or an `R_AARCH64_RELATIVE` entry pointing at it, so
they are dead code and patching them changes nothing.

## 4. Expected device log

`dm/gfx/nvn/hle_nvn.c:1290` prints the first swap-chain texture:

```
[nvn] WindowInitialize swap chain 3 textures, interval 1, first 1920x1350 format 0x…
```

Before the patch the same line says `1920x1080`. The swap chain is built from the
hard-coded pair, so this line is the direct proof that the rows applied.

## 5. Present and what to look for visually

With the canvas at 1.4222 and the drawable at 1.4215 the ratio difference is
0.05 %, under the 1 % rule at `nvn_mtl.m:11129`, so the whole canvas is used with
no bars and no anisotropy (`2853/1920 = 1.486`, `2007/1350 = 1.487`).
`DM_PRESENT_FILL=stretch` becomes a no-op; leaving it unset is the honest test.

Expected picture: 25 % more vertical world, no horizontal squeeze, HUD
undistorted (it is laid out against the same canvas via the patched int pair).

## 6. Residual risk and where to look next

* If the log shows `1920x1350` but the picture is still squeezed, the engine has a
  third size source. The next places, in order: the per-view rect pushed to
  `nvnCommandBufferSetViewport` from the display object (the writers of
  `+0x7e8`-style view rects in the renderer object created at `0x40b690`), and
  the UI table at `0x13e7c30` whose entries are keyed by `{1920,1080}`,
  `{1600,900}` and `{1422,800}` — if the UI scaler refuses to pick an entry for
  `{1920,1350}` the HUD may fall back to the 1080 entry; the fix then is to add a
  `{1920,1350}` entry or to point `[renderer+0xa58]` at the 1920x1080 entry
  explicitly (the selector is `0x8023e0`, the index arithmetic `0x802420`).
* If the log still shows `1920x1080`, the rows were not applied (the assert would
  have failed first, so this means the image was rebuilt from another build).

## 7. Reproducing the evidence

```sh
python3 dm/tools/nso.py <ExeFS>/main /tmp/sm3dw.bin
python3 dm/tools/sdis.py /tmp/sm3dw.bin 0x40b7f0 50     # the pair and bl 0x711a80
python3 dm/tools/sdis.py /tmp/sm3dw.bin 0x711a80 60     # agl display init: +0x110/+0x114
python3 dm/tools/sdis.py /tmp/sm3dw.bin 0x719970 40     # swap-chain builder reads +8/+0xc
python3 dm/tools/sdis.py /tmp/sm3dw.bin 0x719d00 20     # SetTextures + WindowInitialize
```
